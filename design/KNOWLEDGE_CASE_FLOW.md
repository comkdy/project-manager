# 자연어 평가 사례와 데이터 연결 중심의 AI 지식 설계

작성: 2026-10-25 · 상태: 설계안. 이 문서는 현재 앱의 구현 완료를 의미하지 않는다.

## 1. 결정

평가 사례는 **적용 범위와 자연어만으로 등록**한다. AI는 원문에서 관측과 조건을 정리하고, 기존 AI 지식을 통해 용어를 실제 데이터에 연결한다. 불명확한 의미는 기존 **확인 요청**의 같은 항목에서 묻는다. 사용자는 구조화된 필드를 직접 편집하지 않고 자연어로 설명하거나 수정한다.

저장의 중심은 ‘원인 → 결과’ 화살표가 아니라 **조건과 근거가 있는 관측 기록**이다. 사람이 사례를 승인했다는 사실, 용어의 데이터 연결이 확인됐다는 사실, 현재 데이터에서 결과가 재현됐다는 사실은 서로 다르다.

LLM Wiki의 누적 정리 방식은 활용하되, 승인된 원문·관측·데이터 연결을 바탕으로 생성하는 읽기 쉬운 설명에 적용한다. Wiki 문서 자체를 새로운 독립 증거나 인과관계의 확정 근거로 취급하지 않는다.

## 2. 현재 구현에서 바꿔야 할 부분

소스 확인 결과:

| 현재 구조 | 사용자에게 생기는 문제 | 변경 방향 |
| --- | --- | --- |
| `EvaluationRegistration.tsx`, `EvaluationInput`이 데이터셋 선택을 필수로 요구 | 데이터셋을 아직 만들지 않았거나 여러 원천에 걸친 사례를 등록하기 어려움 | 등록에서 데이터셋 선택 제거. 공통/기존 프로젝트와 원문만 필수 |
| `evaluation_extraction.py`가 원문의 문장을 공정·Recipe·Inline·EPM 등 고정 필드로 분류 | 문장은 보존하지만 용어가 실제 어떤 측정값인지, 여러 조건이 함께 작용하는지 표현이 부족 | 원문 근거를 유지하면서 관측·조건·등장 용어·데이터 연결 후보를 추출 |
| `SemanticCollection.tsx`의 `DraftReview`가 내부 필드를 다수 노출 | 무엇을 판단해야 하는지 불분명 | 짧은 해석, 필요한 질문, 자연어 수정, 승인으로 축소 |
| `evaluations.py`의 검색이 최초 데이터셋과 스냅샷에 강하게 의존 | 다른 데이터셋에서 같은 의미의 변수를 보고 있어도 사례 재사용이 제한됨 | 적용 범위·의미·조건으로 사례 검색. 현재 데이터 연결의 유효성은 별도 검사 |
| 기존 `relation` 지식은 테이블 결합 관계를 뜻함 | 과학적 관계와 혼용하면 잘못된 결합이나 인과 해석 가능 | 데이터 결합 지식은 그대로 유지하고, 사례의 관측 관계를 별도 내용으로 표현 |

기존 질문·답변·초안·승인·버전·실행 작업자를 확장한다. 프로젝트, 데이터셋·쿼리 작성, 대시보드·카드 편집, 기존 채팅 기능의 사용 흐름은 이번 변경 범위에 포함하지 않는다.

## 3. 사용자가 경험하는 흐름

### 등록

입력은 두 가지다.

1. **적용 범위:** 공통 / XXXA / XXXB / XXXC 등 기존 프로젝트.
2. **평가 내용:** 평소 동료에게 설명하듯 자연어로 작성.

예: “Operation A에서 Recipe 1, 2, 3을 비교했더니 Inline CD의 alpha가 증가했고 EPM parameter1은 감소했다. 같은 장비를 썼는지는 확인이 필요하다.”

제목, 관측 항목, 조건, 관계는 AI가 제안한다. SQL, 데이터셋, 컬럼, 관계 종류를 입력 폼에 요구하지 않는다. 사용자가 아는 자료 출처나 기간은 본문에 함께 적을 수 있다.

**공통은 여러 프로젝트에서 참고할 수 있다는 뜻**이다. 모든 제품·장비에서 결과가 성립한다거나 데이터 열람 권한이 확대된다는 뜻은 아니다. 적용 범위와 평가 당시의 제품·장비·기간은 따로 보존한다. 사용자가 범위를 바꾸기 전에는 AI가 공통으로 승격하지 않는다.

### 확인 요청

하나의 사례를 하나의 항목에서 끝까지 처리한다. 기존 두 종류를 유지한다.

- **추가 설명 필요:** 해석이나 데이터 연결에 중요한 질문이 있음.
- **승인 필요:** 사용자가 AI의 이해 내용을 확인하면 됨.

열었을 때 기본 화면은 다음 순서다.

1. **AI가 이해한 내용:** 2~4문장. 무엇을 비교했고 무엇이 관측됐는지, 무엇은 아직 모르는지.
2. **지금 확인할 내용:** 가장 중요한 질문 1~2개. 질문마다 왜 필요한지 한 문장.
3. **자연어 답변/수정:** 하나의 입력란. “이렇게 이해하면 돼”, “alpha는 …야”, “장비 정보는 몰라”처럼 답변.
4. **승인:** 검토할 내용이 준비되면 “이 내용으로 승인”. 승인 대상은 보고 내용의 정리이며 인과관계의 확정이 아님을 짧게 표시.

원문·답변 이력·실제 데이터 연결·계산 근거는 하나의 ‘근거와 상세 내용’ 펼침 영역에 둔다. 여러 경고 박스와 편집 박스를 반복 배치하지 않는다. 기술 상세가 필요한 사용자는 열어볼 수 있다.

자연어 수정 뒤에는 바뀐 부분만 짧게 보여 준다. 답변하는 행위만으로 자동 승인하지 않는다. 새 답변으로 기존 승인 내용이 달라지면 새 버전을 검토하며, 이전 버전을 덮어쓰지 않는다. 기존 승인 권한을 유지한다.

### 일부를 모를 때

**사례 보관과 분석 준비를 분리**한다. “장비는 모른다”라고 답했더라도 보고된 관측은 그 한계와 함께 승인할 수 있다. 다만 장비별 비교를 실행할 준비가 됐다고 표시하지 않는다.

| 상태 | 가능한 일 | 하지 않는 일 |
| --- | --- | --- |
| 관측 내용 승인, 일부 용어 연결 없음 | 과거 보고로 검색·설명하고 현재 분석에 필요한 연결을 질문 | 연결되지 않은 측정값을 임의로 선택해 계산 |
| 관측 및 데이터 연결 확인 | 실행 가능한 비교를 제안 | 조건이 다른 현재 데이터에서 같은 효과가 재현됐다고 단정 |
| 현재 데이터 분석 완료 | 수치·조건·표본·실행 근거와 함께 결과 설명 | 계산이 끝났다는 이유만으로 원인 확정 또는 자동 승인 |
| 현재 결과 검토·승인 | 원래 사례와 연결된 재현/차이 사례로 축적 | 과거 사례를 새 결과로 덮어쓰기 |

‘모름’과 ‘나중에 확인’은 유효한 답변이다. 같은 질문을 매 방문마다 반복하지 않는다. 새 자료가 들어오거나 사용자가 그 정보가 필요한 분석을 요청할 때 다시 확인한다.

## 4. 자연어와 실제 데이터의 연결

기존 AI 지식의 용어, 별칭, 지표 정의, 데이터 연결을 먼저 사용한다. 그다음 접근 가능한 데이터 목록·컬럼·형식과 필요한 범위의 값 후보를 확인한다. 이름이 비슷하거나 값이 존재한다는 이유만으로 의미가 같다고 확정하지 않는다.

연결할 대상은 단순한 컬럼 하나가 아닐 수 있다. 예를 들어 세로형 측정 데이터에서 ‘Operation A의 alpha CD’는 다음을 함께 알아야 한다.

- 어떤 원천 또는 데이터셋을 사용하는가.
- 어느 컬럼이 수치인가.
- 어떤 공정·측정 항목의 값만 선택하는가.
- 단위, wafer/lot/die 등 측정 단위, 측정 시점은 무엇인가.

‘alpha = MAIN’, ‘Operation A = operA CD’ 같은 연결은 설명용 예시일 뿐 현재 DB에서 확인된 사실로 취급하면 안 된다. 연결 후보가 여러 개면 사용자가 알아들을 수 있는 표현으로 묻는다.

> “alpha는 A 공정의 CD 측정 항목을 뜻하나요? 이름이 비슷한 항목이 두 개 있습니다. 사용하던 보고서의 항목명이나 측정 의미를 알려 주세요.”

사용자가 DB 컬럼을 모르면 보고서 용어·단위·공정 의미로 답해도 된다. 그래도 식별할 수 없다면 후보를 미정으로 남긴다. 필요하면 같은 확인 요청에서 데이터 담당자가 답할 수 있지만, 자동으로 다른 사람에게 메시지를 보내지는 않는다.

확정된 연결은 사례의 텍스트에만 묻어 두지 않고 재사용 가능한 AI 지식으로 저장한다. 동일한 단어도 프로젝트·공정·시기에 따라 의미가 다르면 별도로 관리한다. 공통 연결과 프로젝트 연결이 충돌하면 조용히 한쪽을 선택하지 않고 현재 맥락에 맞는 의미를 확인한다.

### 질문을 만드는 기준

- 잘못 연결하면 결론이 바뀌는 모호성부터 질문한다.
- 현재 요청에 필요하지 않은 장비·기간·표본 정보를 등록 시점부터 전부 요구하지 않는다.
- 같은 의미·범위·데이터 정의에 대한 질문은 모아 한 번의 답변을 재사용한다.
- 여러 질문이 독립적이면 가장 중요한 1~2개부터 제시한다. 답변으로 해결된 질문은 종료한다.
- 실제 장비 컬럼이 없으면 ‘분석에 사용할 장비 정보 없음’으로 표시한다. 공정 이력이라는 이유만으로 장비 정보가 있다고 가정하지 않는다.

### 데이터 결합

Inline과 EPM을 비교하려면 wafer 식별자뿐 아니라 lot, 공정 순서, 재측정, 재작업, 측정 시점 등이 맞아야 한다. 다대다 결합으로 표본이 부풀거나 나중 측정값이 앞선 조건에 섞이지 않도록 기존 결합 지식을 재사용한다. 대응 규칙이 없거나 모호하면 같은 확인 요청에서 먼저 확인한다.

현재 데이터셋이 바뀌었다고 과거의 보고 자체를 폐기하지 않는다. 과거 보고의 출처는 유지하고, 현재 스키마에 대한 데이터 연결과 실행 가능 여부만 다시 검사한다. 반면 실제 계산 결과의 원본 실행·데이터 버전·필터·스냅샷은 계속 고정해 보존한다.

## 5. 복잡한 관계를 표현하는 방법

### 하나의 평가에 여러 요인을 함께 보존

다음 사례를 독립적인 두 화살표로 쪼개지 않는다.

> “XXXA에서 장비 E1을 쓸 때만 Recipe 2가 CD 증가와 EPM 감소를 보였다. E2에서는 차이가 없었다.”

이 사례는 제품·장비·Recipe 조합에 따라 달라지는 **조건부 관측 묶음**이다. 비교 대상, 여러 관측값, ‘차이 없음’, 기간, 원문 근거를 함께 저장한다. 일부 조건만 떼어내 일반 법칙으로 만들지 않는다. `RCP1/2/3`의 숫자 역시 사용자가 순서나 물리적 강도를 설명하지 않았다면 범주 이름이다.

내부 기록에는 다음을 갖춘다. 일반 사용자가 이 항목들을 직접 채우지는 않는다.

| 내용 | 예 |
| --- | --- |
| 등장 대상과 역할 | 변경한 Recipe, 관측한 CD/EPM, 조건인 장비·제품 |
| 비교와 조건 | 같은 공정, E1에서 Recipe 1 대 Recipe 2, 특정 기간 |
| 관측 | 증가, 감소, 차이 관측 안 됨, 불명확; 보고에 있는 수치만 |
| 관계의 성격 | 함께 변함, 시간적으로 선행, 측정 대리 지표, 가능한 설명 가설 |
| 근거 | 원문 구절·답변 버전, 또는 계산 실행·방법·데이터 버전 |
| 한계 | 표본 수 미기재, 장비 조건 미확인, 제품 한정 등 |

조건은 ‘A와 B가 함께’인지 ‘A 또는 B’인지 구별하고, 미기재와 ‘해당 없음’도 구별한다. 상호작용이나 조건부 효과를 표현할 수 있도록 여러 대상을 묶는 기록으로 저장한다. 저장소를 별도 그래프 DB로 바꿀 필요는 없다.

### 관측과 원인 가설을 분리

‘Recipe 변경, CD 증가, EPM 감소’만으로 다음 중 하나를 고를 수 없다.

- Recipe 변경으로 공정 상태가 달라졌고, CD와 EPM이 그 영향을 각각 반영했을 가능성.
- 함께 바뀐 장비 상태나 lot 특성이 CD와 EPM 양쪽에 영향을 줬을 가능성.
- 제품·기간·선택 표본의 차이가 겉보기 관계를 만들었을 가능성.

특히 **Inline 계측값은 공정 상태를 보여 주는 대리 지표일 수 있다. 측정값 자체가 EPM을 바꾸는 원인이라고 볼 수는 없다.** 가능한 설명은 ‘가설’로 제안하고, 관측 사실과 다른 종류로 보관한다. LLM이 만든 가설이 사용자 승인만으로 인과적으로 검증된 사실이 되지 않는다.

재작업이나 피드백이 있으면 같은 변수라도 공정 전·후와 시점을 구별한다. 과거 결과를 보고 다음 Recipe를 바꾼 기록을 하나의 정적인 원인 화살표로 합치지 않는다.

### 반례와 불일치

새 사례가 반대 결과를 보이면 기존 사례를 수정해 지우지 않는다. 조건이 다르면 ‘조건에 따라 달라질 가능성’, 조건이 유사하면 ‘서로 다른 결과가 보고됨’으로 연결한다. 서로 독립된 평가인지도 확인한다. 같은 보고서를 요약한 문서 여러 개를 반복 재현의 증거로 세지 않는다.

‘승인 여부’, ‘데이터 연결 확인 여부’, ‘보고/계산/실험이라는 근거 종류’를 따로 관리한다. 근거 없이 하나의 ‘신뢰도 92%’로 합치지 않는다.

## 6. 실제 분석으로 이어지는 방식

1. 사용자의 질문과 현재 선택한 데이터·카드·필터를 받는다.
2. 접근 가능한 공통/프로젝트 사례 중 의미와 적용 조건이 관련된 기록을 찾는다.
3. 현재 데이터에 연결 가능한 변수, 빠진 연결, 조건 차이를 확인한다.
4. 가장 구분력이 있는 소수의 분석을 이유와 함께 제안한다. 예: 장비별로 나눠 Recipe 비교, 같은 조건에서 CD–EPM 관계 확인.
5. 필요한 데이터만 읽기 전용 조회·피벗하여 기존 작업자에서 수치를 계산한다. LLM에는 계산 요약, 범위, 결측·표본 정보와 근거를 전달한다.
6. 결과를 원래 사례와 대조하고, 결과 검토는 같은 확인 요청 체계를 이용한다. 승인 후 새 근거로 축적한다.

원문 해석/용어 연결을 위한 질문과 수치 분석 실행은 다른 작업이다. 새 사례를 올릴 때마다 전체 PARA를 분석하지 않는다. 관련 사례·새 답변·변경된 데이터 연결에 한정해 정리 작업을 실행한다.

초기 분석은 기존 그룹 비교와 상관관계를 정직하게 설명하는 것부터 시작한다. 분석 결과로 표시하는 수치는 기존 서버 계산을 사용하고 LLM이 생성하지 않는다.

인과 효과 추정이 필요해지면 무엇을 바꾸었을 때 무엇이 얼마나 달라지는지를 먼저 정의하고, 시간 순서·비교군·혼란 요인에 대한 가정과 추정 가능성을 확인해야 한다. DoWhy가 제시하는 모델링→식별→추정→견고성 확인 순서를 참고할 수 있다.[3] 모든 컬럼을 무조건 보정하는 것은 해법이 아니다. Recipe의 전체 효과를 묻는 분석에서 중간 단계인 Inline을 보정하면 관심 효과의 일부를 제거할 수도 있다.

wafer 내 여러 die나 같은 lot의 관측을 독립적인 반복 실험처럼 세지 않도록 표본 단위를 확인한다. 예측 모델이나 변수 중요도는 후보를 좁히는 도구이며 인과관계의 증명이 아니다.

## 7. LLM Wiki와 GraphRAG의 적용 범위

Karpathy의 LLM Wiki는 원문을 보존하고 새 자료가 들어올 때 연결된 설명 문서를 점진적으로 갱신하는 **설계 패턴**이다. 특정 구현이나 이 앱의 정확도를 입증한 연구 결과는 아니다.[1]

이 앱에는 다음 세 층이 적합하다.

1. **원문과 실행 근거:** 원문, 답변, 계산 결과를 버전과 함께 보존.
2. **검토된 지식:** 용어·데이터 연결·관측·조건·가설과 그 상태를 구조적으로 저장.
3. **읽기 쉬운 설명:** 특정 공정/측정 항목에 대해 알려진 관측, 조건별 차이, 모르는 점, 관련 사례를 요약.

3번은 1·2번에서 다시 만들 수 있는 자료다. 각 설명은 근거로 돌아갈 수 있어야 한다. 설명을 다시 읽어 새 근거로 추가하는 순환을 만들지 않는다. 요약이 잘못됐을 때는 원문과 승인 기록을 기준으로 복원한다. 새 사례가 영향을 주는 설명만 갱신하고 실패 시 이전에 유효했던 설명과 갱신 필요 상태를 유지한다.

GraphRAG는 문서에서 개체·관계를 추출하고 연결 구조와 요약을 검색에 활용한다.[2] 관련 항목을 따라 사례를 찾는 아이디어는 참고하되, 그것이 인과적 사실을 보증하지는 않는다. 처음부터 전체 GraphRAG 파이프라인이나 별도 그래프/벡터 서비스를 도입하지 않는다. 기존 PostgreSQL의 구조화 내용·용어 검색·제한된 관련 항목 탐색으로 시작하고, 실제 검색 누락·오탐·처리 비용을 비교해 추가 여부를 판단한다. 이용자 수만으로 기술의 필요 여부를 결정하지는 않는다.

새 Wiki 메뉴는 필요 없다. 기존 AI 지식의 항목 설명과 채팅 답변에서 이 누적 설명을 사용한다. 열람 권한과 범위는 검색 전에 적용하고, 프로젝트 전용 근거가 공통 요약에 섞이지 않도록 한다.

## 8. 기존 구조와의 연결 및 이전

아래는 전체 변경 계획이다. 2026-10-25에 1순위인 입력·확인 경험과 최소 용어 연결을 구현했으며, 운영 데이터의 기존 원문·ID·승인 상태는 보존했다. 전체 관계 모델과 누적 설명은 후속 범위다.

- 평가 등록에 명시적인 `case_context`를 추가한다. 적용 범위는 기존 프로젝트 식별자로 저장한다. 기존 데이터셋 질문과 새 평가 사례 질문의 문맥을 구분하고 평가 사례에서는 데이터셋을 선택 사항으로 둔다. 가짜 데이터셋을 만들지 않는다.
- 기존 `KnowledgeQuestion` / `KnowledgeAnswer` / `CollectedDraft` / `KnowledgeVersion`의 수집·답변·승인·버전을 재사용한다. 재사용할 용어와 실제 데이터 연결은 기존 지식·Binding 구조를 확장한다.
- 관측 기록은 버전이 있는 평가 내용 안에 저장하고, 검색에 필요한 관계 색인만 추가한다. 초기부터 별도 관계 관리 시스템을 만들지 않는다.
- 기존 사례의 원문, ID, 승인 이력, 최초 데이터셋 스냅샷을 보존한다. 기존 프로젝트 범위를 초기 적용 범위로 옮기되, 더 넓게 공개하거나 불명확한 연결을 자동 승인하지 않는다.
- 자연어 사례의 재사용 가능성과 계산 결과의 원본 유효성 검사를 분리한다. 기존 실행 결과의 수치 위조 방지, 데이터 버전 확인, 승인 권한과 동시 수정 방어는 그대로 유지한다.
- 답변 처리에는 답변 버전과 사용한 지식 버전을 기록한다. 오래된 처리 결과가 최신 답변을 덮어쓰지 못하게 하고, 같은 요청의 재시도로 중복 지식이 생기지 않게 한다.
- 용어 정의나 스키마가 바뀌면 영향을 받는 연결·제안·설명만 다시 확인한다. 사용자에게 알리지 않고 과거 승인 내용의 의미를 바꾸지 않는다.

## 9. 구현 우선순위와 통과 기준

### 1순위: 입력과 확인 경험, 최소한의 용어 연결

범위+원문 등록, 데이터셋 없는 사례 문맥, 간결한 확인 화면, 자연어 수정, 기존 승인 용어 우선 사용, 모호한 용어 질문을 한 묶음으로 구현한다. 데이터 연결 미완료 사례도 저장·승인할 수 있게 한다. UI만 바꿔 내부 필드 편집을 숨기는 것으로 완료하지 않는다.

### 2순위: 조건부 관측과 재사용

여러 요인의 조합, 차이 없음, 부정, 불명확성을 표현하고 용어 연결을 다른 사례에서도 재사용한다. 사례 검색을 데이터셋 중심에서 의미·범위·조건 중심으로 옮긴다. 반대 결과를 보존하고 조건 차이를 설명한다.

### 3순위: 누적 설명과 분석 제안 개선

검토된 기록으로 항목별 설명을 갱신하고, 현재 데이터에 실행 가능한 비교를 우선 제안한다. 계산·결과 검토·지식 축적을 기존 흐름에 연결한다. 고급 인과 추정은 필요한 데이터와 가정을 확보한 구체적 문제에서 별도로 검토한다.

최소 검증 시나리오:

| 시나리오 | 기대 결과 |
| --- | --- |
| 데이터셋을 만들기 전 공통/프로젝트 사례 등록 | 원문 보존, 올바른 범위, 정상 확인 요청 생성 |
| 등록된 별칭과 단위로 측정 항목 식별 | 기존 승인 연결 재사용, 불필요한 반복 질문 없음 |
| 같은 용어가 여러 공정/항목에 존재 | 임의 확정 없이 짧은 질문, 자연어 답변 후 해석 갱신 |
| 값 컬럼과 항목 식별 컬럼이 따로 존재 | 공정·항목 필터까지 연결; 다른 측정값 혼합 없음 |
| 장비 정보 없음 / 사용자가 모른다고 답함 | 관측은 보존, 장비 분석은 미준비, 반복 질문 억제 |
| ‘E1에서만 증가’, ‘차이 없음’, ‘관련 있다고 볼 수 없음’ | 조건·부정·미확정 보존; 단순 원인 화살표로 변환하지 않음 |
| 같은 사례의 답변/승인이 겹쳐 처리됨 | 오래된 결과 반영·중복 승인 차단 |
| 데이터셋/스키마 변경 | 원문 사례 유지, 영향받는 연결 재확인, 과거 계산 근거 보존 |
| 다른 프로젝트 또는 접근 불가 원천 | 검색·요약·질문 후보에서 권한과 범위 유지 |
| 새 결과가 과거 사례와 다름 | 두 근거 유지, 조건 차이·불일치 표시 |
| 기존 프로젝트·쿼리·데이터셋·카드·채팅·승인 흐름 | 기존 회귀 검사 및 실제 화면 연계 검사 통과 |

품질 평가는 정답이 정해진 작은 평가 사례 묶음으로 시작한다. 올바른 연결 비율, 모호한 상황에서 임의 연결한 비율, 꼭 필요한 질문의 누락/반복, 근거 없는 관계 생성, 사례당 호출 수와 대기 시간을 함께 본다. 고정 응답을 쓰는 흐름 검사와 실제 LLM의 해석 품질 검사는 구분한다.

## 10. 참고 자료와 판단의 구분

### 2026-10-25 추가 방향: 사용자 지식 축적에서 지속 분석으로

초기에는 엔지니어가 사례와 용어·측정 의미를 제공하고, 시스템은 실제 데이터 연결을 확인한다. 이후 자동화 준비 여부는 사례 개수가 아니라 분석 대상의 연결·표본 단위·시간 대응·비교 조건이 확인되었는지로 판단한다. 준비된 대상부터 다음 순환을 실행하는 것이 후속 구현 목표다.

`새 데이터/변경 감지 → 관련 지식과 분석 질문 선택 → 필요한 범위 조회·피벗 → 통계·ML 작업자 → 과거 근거와 비교 → 새 관측 후보 → 확인 요청/검토 → 승인 지식 → 다음 분석`

- LLM은 질문·변수·조건을 고르고 수치 요약을 설명한다. 계산은 제한된 읽기 전용 조회와 작업자가 수행한다. 원시 데이터 전체를 매번 LLM에 보내지 않는다.
- 기존 그룹 비교·상관관계 다음으로, 다변수 회귀 또는 트리 모델을 후보로 비교한다. 목적은 단일 상관으로 놓치는 조건별 차이·상호작용과 예측에 도움이 되는 변수 후보를 찾는 것이다. 모델 종류는 실제 데이터와 검증 결과에 따라 선택한다.
- wafer/Lot 단위를 지키고 측정 시점 이후의 정보가 과거 예측에 들어가지 않게 한다. 미래 기간 또는 별도 Lot에서 성능을 확인하며 단순 기준 모델보다 나은지도 비교한다. 그룹·시간 의존 데이터의 무작위 분할은 성능을 부풀릴 수 있다.[4]
- 변수 중요도는 원인 확정값으로 표시하지 않는다. 서로 비슷하게 움직이는 변수가 있으면 중요도가 분산되거나 낮게 보일 수 있다.[5] Recipe 전체 효과와 Inline을 통한 간접 경로처럼 질문이 다른 분석을 구분하며, 인과 효과는 가정·식별·견고성 검토가 가능한 경우에만 별도 추정한다.[3]
- 계산 결과는 실행 근거로 자동 보존하되, 확인되지 않은 새 관계를 승인 지식으로 자동 승격하지 않는다. 반복 관측은 누적하고, 새로운 의미·기존 사례와의 충돌·판단이 필요한 변화는 확인 요청으로 보낸다. 관측되지 않은 장비 상태를 측정한 것처럼 추정하지 않는다.
- 처음에는 연결된 소수의 관계부터 변경분 중심으로 실행한다. 실행량 한도·중복 방지·기존 작업 재시도/취소·정기 분석을 재사용한다. 지식이 적더라도 데이터 연결이 준비된 대상의 탐색은 가능하며, 사용자 사례는 탐색 우선순위를 정하는 근거다.

**구현 상태:** 범위+원문 등록, 기존 승인 지식의 용어 연결, 자연어 확인 요청, 기존 분석 실행→결과 검토→승인 지식 흐름까지 구현되어 있다. 분석 수치는 현재 그룹 통계와 Pearson 상관관계다. 변경 데이터를 지속 반영하며 AI가 다음 질문을 선택하는 자율 분석, ML 학습·검증, 조건별 관계의 누적 설명은 아직 구현하지 않았다. 기존 고정 조건의 정기 실행과 구분한다.

- [4] [scikit-learn 교차 검증 안내](https://github.com/scikit-learn/scikit-learn/blob/main/doc/modules/cross_validation.rst): 그룹·시간 의존 자료의 검증 분할. wafer/Lot 적용 방식은 이 앱을 위한 설계 제안이다.
- [5] [scikit-learn 상관된 변수의 중요도 예제](https://scikit-learn.org/stable/auto_examples/inspection/plot_permutation_importance_multicollinear.html): 상관된 입력에서 중요도 해석의 한계.
