# Project Manager implementation contract

All HTTP endpoints use `/api`. JSON uses snake_case. Company-verified SSO cookie authentication; local demo mode automatically resolves the test administrator. Vite proxies `/api` to 127.0.0.1:8000. Errors are `{detail: string}`. IDs for projects are integers; other IDs are strings. Dataset versions are integers. Original source is read-only. App metadata is a separate PostgreSQL database.

### DB settings

- `GET /database-status` (authenticated): live read-only connectivity status, `workspace_token`, `connection_key`, `profile_id`; no credentials.
- `GET /admin/databases`: saved PostgreSQL profiles (`id,host,port,database,username,sslmode`), active ID and workspace token. An existing environment connection is listed until persisted.
- `POST /admin/databases/test` and `/mount`: `{profile_id?,host,port,database,username,password?,sslmode?}`. A blank password reuses a saved credential only for the same endpoint and user. Test validates connection, SELECT-only role, and catalog access without saving. Mount validates/discovers before atomically persisting the selection; failure leaves the previous DB active.
- `POST /admin/databases`: the same connection body validates and saves a profile without switching the active DB. Editing the already-active DB reapplies its settings after validation. Returns `{profile_id,active,workspace_token,table_count,status}`.
- `POST /admin/databases/{profile_id}/activate`: activates a registered profile using stored credentials. A single persisted mount row is updated under a transaction lock, so activation replaces the previous DB for the entire app. Discovery failures leave the old selection intact. The UI separates registration from this explicit activation action.
- `DELETE /admin/databases/{profile_id}`: admin-only unregister; rejects the persisted active DB with 409 and unknown/deleted IDs with 404. Deletes the stored connection and encrypted credentials without opening a source connection. Preserves workspace definitions and table visibility; a credential-free removal marker prevents automatic env reimport. Explicit re-registration with credentials clears the marker.
- `GET /admin/databases/{id}/tables`: all readable non-system tables, including hidden ones, with `schema_name,table_name,columns,primary_key,visible`.
- `PUT /admin/databases/{id}/table-visibility`: `{schema_name,table_name,visible}`. Persists per-DB visibility and refreshes the active workspace without deleting definitions. Returns `active,visible,workspace_token`. Names are stored as schema/table pairs.
- All `/admin/databases` routes require an administrator. Credentials are encrypted with a separate Fernet key and are never included in JSON responses or audits.
- Source requests retain an immutable engine/DB identity/visibility snapshot. Browser requests carry `X-Workspace-Token`; stale workspace requests are rejected with 409. Bootstrap/status/DB management can refresh the selection. Source query caches include the workspace revision.

## Shared types

Filter: `{column: string, op: 'eq'|'ne'|'gt'|'gte'|'lt'|'lte'|'in'|'contains', value: unknown}`.

QueryContext: `{project_id?: number|null, filters?: Filter[], limit?: number, cursor?: string|null, sort?: string, direction?: 'asc'|'desc', refresh?: boolean}`.

DatasetSpec: `{source_id: string, columns?: {name: string, expression: string}[], filters?: Filter[], joins?: string[], join_types?: Record<string,'left'|'inner'>, where_sql?:string|null, group_by?:string[], having_sql?:string|null, raw_sql?: string|null}`. Empty form columns means all registered input columns; normalization expands them. A nonempty list is the complete output projection. Expressions refer to source names or `<right_source_id>__<column>` for joined fields. Registered joins are many-to-one, selectable by relation ID. All joins originate at the base source; repeated target tables are unsupported.

Raw mode requires all form fields empty: a single SELECT from the registered source, optional registered LEFT/INNER JOINs, WHERE, GROUP BY and HAVING. Aggregates: COUNT/SUM/AVG/MIN/MAX, COUNT(DISTINCT one expression), aggregate FILTER. JOIN ON must match registered key equalities; server adds project-key equality and scopes each input. No arbitrary JOIN, SELECT DISTINCT, CTE, subqueries, windows, ORDER/LIMIT, locking or writes. AST validation produces one canonical form definition and bound SQL; raw text is never directly executed. Save persists normalized form fields with raw_sql=null. Both editors round-trip through the same compiler. Legacy output filters are substituted into WHERE or HAVING. Invalid SQL keeps its draft in the SQL editor.

For grouped definitions, common context filters on available input columns run before aggregation. Card/output filters run after aggregation. Each group carries MIN(text input primary key) as a hidden cursor key; the registered many-to-one invariant keeps group keys distinct. Grouped preview before_rows is a source sample after WHERE, before HAVING, not a one-to-one comparison with grouped results (meta.before_mode='source_sample').

Dataset summary: `{id,name,version,project_id:number|null,columns:[{name,type}],spec}`. NULL means shared. A project-owned dataset retains its owner across versions. Its stored owner is applied when query context omits project_id; a mismatching project is rejected. The base source is project-filtered before raw predicates or expressions. Shared source tables with no project column remain shared and report an ignored project filter. Common boards may use only shared definitions, and project boards may use shared or their own definitions. Cards query the latest dataset version; the saved dataset_version is not a runtime pin. Chart responses report the version actually used.

CardSpec: `{id,title,dataset_id,dataset_version,kind,renderer,x?:string,y?:string,color?:string,aggregate:'count'|'sum'|'avg'|'min'|'max'|'yield'|'none',filters:Filter[],options:{palette?:string,bins?:number,sort?:'asc'|'desc',x_min?:number,x_max?:number,y_min?:number,y_max?:number}}`. Kind = `kpi|scatter|bar|line|histogram|box|heatmap|wafer`. Renderer = `plotly|seaborn`. Layout is separate: `{i:string,x:number,y:number,w:number,h:number}`.

Chart result: `{rows:[{x?:unknown,y?:unknown,color?:unknown,value?:number}],meta:{mode:'full'|'sample'|'aggregate',returned_rows:number,queried_at:string,cached:boolean,ignored_filters:string[],...}}`. kpi row has `value`. Bar/line rows have x,y and optional color. Scatter/box rows x,y,color. Histogram rows x,y (server bins/count). Heatmap/wafer rows x,y,value. SQL aggregation, limited results, no full dataset download.

## API

- Evaluation cases: `POST /semantic/collection/evaluations` accepts `{project_id: number|null, text}` without a dataset. Existing `{dataset_id, text}` clients remain supported; do not supply both dataset_id and an explicit project_id. Scope is validated against the current source's projects. New cases expose `dataset: null` and `case_context: {project_id}`; old dataset snapshots are unchanged. The internal tagged context uses the existing JSON storage, without schema migration or placeholder datasets.
- Evaluation term references come from approved, scoped knowledge and are checked against the original answer, knowledge version, and binding fingerprint. Ambiguous terms become follow-up questions in the same confirmation request. A natural-language explanation without an approved physical binding remains unlinked. New answers invalidate outdated drafts; approval retains revision, role, source, and computed-result checks. See `EVALUATION_CASES.md` and `validation/natural-evaluation.md`.

- Scheduled analyses: see `SCHEDULED_ANALYSIS.md`. Canonical `analytics/schedule_contract.py` generates `analysisSchedules.generated.ts`. `GET /analytics/schedules`, `POST /analytics/schedules/preview`, `POST /analytics/schedules`, `POST /analytics/schedules/{id}/actions` (`pause|resume|replace`) and `POST /analytics/schedules/notifications/{id}/ack`. Editor-owned, admin-manageable schedules capture a completed bounded business analysis, source/project scope and approved reference versions. Fixed UTC elapsed intervals shift the original windows to the due time; missed slots coalesce and active executions never overlap. Dispatch uses the existing creation lock/queue/quotas. Failures, cancellation and unresolved criteria pause the schedule. `AnalysisRun.schedule_id` / `scheduled_for` survive retries; the current scheduled retry updates the schedule's last-run pointer without replacing older history. In-app notices compare discrete per-series outcomes and direction, dedupe unchanged outcomes, and preserve acknowledgement. Metadata-only polling defers previously processed result bodies. All writes recheck workspace, account and expected revision. No external notification delivery or source writes.

- `GET /health`: dependencies health.
- `GET /auth/session` -> `{mode:'local_admin'|'sso',status:'authenticated'|'unauthenticated'|'unavailable'|'disabled',user:User|null,message?:string}`. Auth failures return this 200 envelope for the retry screen; protected endpoints retain 401/403/503. `GET /auth/me` -> User. Password login is retired; company-wide SSO logout is not performed by this app.
- User `{id,username,employee_id:string|null,name,team,role:'admin'|'editor'|'viewer',active:boolean,profile_source:'local'|'sso'|'legacy',version:number}`. Username is a compatibility identifier; display name and team come from the internal directory. User roles and active flags are local app policy, never supplied by the browser or overwritten by profile synchronization.

Common scope (omitted project) lists shared definitions; project scope lists only its own definitions. DatasetSummary includes `kind: source|derived`, determined from the generated identity and unchanged direct-table definition. Query execution applies the current project boundary at every physical project source, before joins/aggregates, including authored SQL. Shared-only sources without a project mapping are rejected in project queries. Historical cards may retain their explicit shared definition reference, but execute within the selected project.
- `GET /dashboards?project_id=1` (omit for common) -> `{id,project_id,version,cards:CardSpec[],layout:Layout[]}`.
- `PUT /dashboards/{id}` `{version,cards,layout}` -> updated dashboard; 409 on stale version.
- `POST /query` `{dataset_id,dataset_version,context:QueryContext}` -> `{columns:[{name,type}],rows:object[],next_cursor:string|null,meta:object}`.
- `POST /cards/query` `{card:CardSpec,context:QueryContext}` -> chart result.
- `POST /datasets/preview` `{spec:DatasetSpec,context?:QueryContext}` -> `{columns,rows,before_rows,sql,canonical_sql,spec,meta}`. sql is execution SQL with server CTEs/placeholders; canonical_sql and spec are the editable, normalized definition.
- `POST /datasets/sql` `{spec:DatasetSpec,context?:QueryContext}` -> `{sql,spec,source_tables,project_id,scope_note}`. Authenticated users including viewers may inspect/normalize definitions; this does not execute source data. Both input modes return identical canonical form/SQL including registered joins and the selected project predicate, excluding transient dashboard filters.
- `POST /datasets` `{name,spec,project_id?:number|null}` -> DatasetSummary. `POST /datasets/{id}/versions` `{name,spec,project_id?:number|null,expected_version}` -> new summary; owner changes reject. `GET /datasets/{id}/versions?project_id=1` -> summaries in the requested scope. In project tabs, deriving from a shared dataset creates a new owned definition rather than a shared version.
- `POST /datasets/{id}/impact` accepts the same `DatasetUpdate` body as version saving and requires editor/admin access. It returns the authoritative `DatasetImpact` response from `backend/app/dataset_impact_contract.py`: current/proposed version, added/removed/type-changed output columns, affected current-DB board/card IDs and project names, static compatibility (`compatible|review|incompatible`), issues and limitations. It performs no metadata mutation or card/Python execution. Missing/hidden datasets return 404, stale versions return 409, invalid ownership/specification returns 422 (source schema conflicts may also return 409). The report is a snapshot; saving retains the existing version conflict guard. Generate/check consumer types with `validation/generate_dataset_impact_contract.py [--check]`.
- `POST /render` `{card,context,format:'png'|'svg'}` -> image bytes (same authentication and query path).
- `GET /llm/status` -> `{configured,base_url,model}` (no credentials).
- `POST /chat` accepts message, project/dataset/card context, optional saved-conversation id/revision, `knowledge_context_id`, and `selected_knowledge`. SSE includes `status`, `clarification`, `proposal`, `analysis_proposal`, `evaluation_cases`, `data_analysis`, `error`, `done`, and `conversation` when history is enabled. SQL/card proposals require explicit apply; legacy analysis proposals require explicit condition confirmation. A grounded `data_analysis` request directly queues a bounded read-only calculation; knowledge publication always requires separate review.
- SQL/card `knowledge` metadata is derived from `backend/app/chat_knowledge.py`; models do not author citation names or versions. `ProposalDefinition.knowledge_context_id` retains the server evidence identity for preview/apply revalidation. Absent matching knowledge keeps the existing query flow; ambiguous definitions require selection before query execution.
- Analysis review is defined by `backend/app/analytics/proposal_contract.py`. `GET /analytics/proposals/{id}` revalidates owner/workspace/project/source; `POST /analytics/proposals/{id}/confirm` accepts `AnalysisProposalConfirm` and returns the existing analysis-run response. Same-payload retries return the same run; changed payload after confirmation returns 409. Unsupported method/scope blockers cannot be removed merely by confirming.
- Generated browser contracts: `analysisProposal.generated.ts`, `chatKnowledge.generated.ts`; check using `validation/generate_chat_feature_contracts.py --check`. Historical proposal payloads remain readable and new fields are additive.
- `GET /workspace/activity?project_id=&limit=60` uses the canonical `activity_contract.py` / generated `workspaceActivity.generated.ts` contract. Omitted project means all active projects and common runs; a specified project is exact. Read-only bounded summaries include visible current-DB analyses, pending/cancelled proposals belonging to the current user/role/workspace token, and admin collection state in the all-project view. Stored query and measurement timestamps are distinct; absent evidence stays null. Large analysis results and source measurement rows are not loaded. Legacy source project directories remain supported; an unavailable directory fails closed with 503.
- Browser editing recovery has no server mutation endpoint. Local records are scoped by user/role/workspace/project/kind/target; restore validates editable DTOs and retains the original revision. Pending recovery and changed server revisions require an explicit comparison choice before save. Successful saves clear only the matching stored draft. SQL impact review, card preview, definition review and analysis confirmation retain their existing server checks.
- Admin: `GET /admin/users`, `POST /admin/users` `{employee_id,role,active}`, `PATCH /admin/users/{id}` `{role?,active?,expected_version}`. Only SSO identities are editable. Self-demotion/deactivation, removing the last active SSO admin, and stale versions are rejected. Password/profile modifications are not accepted. `GET /admin/source-tables` -> discovered table descriptors. `GET /admin/sources` -> Source[]. `POST /admin/sources` `{id,name,schema_name,table_name,project_column?,primary_key,columns?:string[]}` (introspection validates). `GET/POST /admin/relations`: `{id,left_source_id,right_source_id,left_column,right_column,join_type:'left'|'inner'}`. `GET /admin/audit`.

Source: `{id,name,schema_name,table_name,project_column:string|null,primary_key:string,columns:[{name,type}]}`. All shared metadata mutations editor/admin; source/account settings admin only. Viewer can query/preview charts but not propose edits via chat or preview/save expressions.

## Knowledge-guided continuous analysis (2026-10-25)

### Chat-requested statistics and ML

- Route `data_analysis` selects `group_compare`, `correlation` or `ml_regression` via the strict `DataAnalysisPlan` schema. An existing evaluation case is optional. The plan cites exact user/approved knowledge/dataset facts, validates actual columns and their roles, and requires row alignment; ML additionally requires earlier features, independent unit columns and a measurement timestamp. User-explicit filters need exact supporting quotes and literal values. No source rows go to the planning model.
- Chat planning settings are discriminated by method: correlation has exactly two metrics and no ML/group fields; grouped statistics have a group column and no ML fields; regression has exactly one target, 1–8 features, 1–4 validation-unit columns and a timestamp. A clarification cannot include settings, column mappings, row-basis claims or a confirmed temporal relationship. Planning context contains only `data_analysis_context`; legacy route/catalog/query-result context is excluded. Rejected responses receive one repair attempt, then fail without running a guessed calculation; diagnostic logs contain bounded validation feedback rather than full responses.
- Candidate datasets are exact-project only. Explicit dataset/card selection is preserved; a dashboard without a selected card sends no arbitrary first-dataset fallback. Existing card filters and applicable period semantics are compiled through the existing evaluation path. Cross-project selection, stale versions, changed source/knowledge bindings and access changes fail closed.
- Server-owned `_chat_analysis` provenance distinguishes chat runs within the existing `AnalysisRun.kind=evaluation` lifecycle. The same bounded statistics/ML worker, quotas, cancellation/retry and result review are reused. `case_ref` is nullable and public views add `origin: chat|case` and optional `question`. Existing case-origin contracts remain unchanged.
- SSE `data_analysis` carries the queued/waiting result reference. `GET /api/chat/data-analysis/{id}?project_id=...` revalidates the original chat scope and owner, returning current status, computed explanation, next checks, dataset/version, filters, result, plan citations and review. Saved chat turns store only `kind` and `run_id`, then re-read authoritative results. A completed result is a timestamped observation, not a claim of continuously fresh data or approved knowledge.
- Unresolved plan connections create ordinary `evaluation-setup:` confirmation questions. Only reviewed/approved answers reach recommendation resumption; a ready resumed chat plan queues automatically. The approved answer basis persists through retries. Missing datasets/project identity remain an actionable chat clarification.
- `submit-review` reuses the existing immutable-result draft and confirmation-request flow. Calculation or model output cannot approve knowledge. The review pins actual computed summaries and source scope; publication requires the existing explicit reviewer action. SQL/dataset/card proposal/apply and historical chat events remain supported.

Initial settings recommendation extends this workflow without new tables:

- `POST /api/evaluation-analysis/{id}/recommend {expected_revision,workspace_token}` returns the current run and schedules bounded background model work. `recommendation.status` is `running|waiting|ready|error`; only `needs_input` runs can request it. A persisted token/expiry prevents late writes and duplicate model calls. Recommendation preparation never queries raw rows or publishes knowledge.
- The model selects from existing typed columns with exact citations to approved case/knowledge or reviewed clarification, plus a row-alignment basis. Unknown columns, invented citations, unsupported group values and incomplete ML grouping/time metadata are rejected. Ambiguities create at most two ordinary term clarification questions with `subject=evaluation-setup:{run_id}`. Their detail includes `analysis_setup {run_id,project_id}` for return navigation.
- Only approved clarification versions enter recommendation context. Their published versions and binding fingerprints are pinned in the run request and preserved in retry/scheduled child requests. Scoped setup explanations are excluded from general SQL/card semantic resolution; they are reused only for the same case/version, dataset definition and project.
- Execute accepts optional `continuous=false,interval_minutes=60`. If a recommendation exists it must be ready and the submitted settings must equal the displayed proposal. A requested watch and initial queued run are committed atomically; repeat execution is idempotent. First-run failures can be retried and their successful child supplies the watch baseline.
- `GET /api/evaluation-analysis?setup_only=true` lists the owner's current-scope pending recommendations across projects for browser recovery. The original project-filtered listing is unchanged without this option.

- Existing evaluation settings add `method=ml_regression`, one `metrics` target, `features` (1–8), `unit_columns` (1–4), and `time_column`. Target/features/units/time must be distinct; actual numeric/time types are checked before execution. Older statistical methods keep their existing contract.
- `POST /api/evaluation-analysis/prepare` accepts optional `explicit_case=false`. Explicit selection validates the exact approved case/version and current scope without requiring keyword ranking. Chat retrieval keeps the default path. Result views optionally include `knowledge_basis`, `data_fingerprint`, and `ml` statistics/validation/importance. No raw rows are exposed by the analysis result.
- `GET /api/knowledge-watches` lists current DB watches for their owner or admin. `POST` accepts `{run_id,expected_revision,workspace_token,interval_minutes=60}` for a completed current result. Creation is idempotent by creator/origin run and adds only `app_knowledge_watches`.
- `POST /api/knowledge-watches/{id}/actions` accepts `{action:pause|resume|check,expected_revision,workspace_token}`. Persisted ownership, active editor role, scope and optimistic revision are checked. Pause stops future checks, not in-flight work; existing job cancellation remains available.
- The existing scheduler reconciles completed runs and checks due watches under the job-creation/workspace/watch lock order. Unchanged content skips dispatch; changed content queues the existing `kind=evaluation` worker. The successful result's fingerprint is the watermark. Failed/cancelled runs pause; retry child runs retain their review connection. Source/data/knowledge/method changes require reconfiguration.
- Completed runs create immutable computed-result confirmation drafts through existing semantic approval rules. Publication always requires approval. Pending-question and existing execution quotas apply. Concurrent scheduler ticks cannot dispatch duplicate children for one change.

## Job controls (existing)

`POST /workspace/activity/actions` accepts canonical `ActivityActionRequest` (`target`, `action: cancel|retry`, `expected_revision`, `workspace_token`) and returns `ActivityActionResult`. The response target identifies the new/existing child for analysis retries. GET activity and analysis responses expose server-owned `controls`; consumers must not infer authorization from status alone. Analysis states add `cancelling|cancelled`; proposal states add `cancelled`. New run fields are additive: `revision`, `cancel_requested_at`, `cancelled_at`, `retry_of`, `retry_run_id`.

Actions revalidate persisted role/ownership and captured workspace/project/source scope under the active-workspace lock. Analysis retry shares the existing creation advisory lock and row lock; one parent produces at most one child. Original requests/results/questions are preserved. A worker checks cancellation during extraction/computation and locks the row before committing results. A cancellation committed first fences late completion/failure. Current DB read/model calls finish at their normal timeout; cancellation is cooperative, not a guaranteed immediate network abort. Expired execution leases are recovered after restart.

Collection uses a distinct `execution_revision` from configuration revision, an execution token, row-locked checkpoints and the existing one-minute cooldown. Cancellation leaves automatic scheduling unchanged. Retry reserves execution before dispatching a background task under the captured source binding. Existing question/answer/review APIs and their conflict rules are unchanged. Additive migrations preserve old metadata; generated types are checked by `generate_chat_feature_contracts.py --check`.
# 정기 분석 이력·저장 결과 비교

계약 기준은 `backend/app/analytics/history_contract.py`, 생성 소비 타입은 `frontend/src/analysisHistory.generated.ts`이다. 기존 `validation/generate_chat_feature_contracts.py --check`에 포함한다.

- `GET /api/analytics/schedules/{id}/history?before={run_id}`: 현재 DB의 소유자/관리자만, 최대 20건과 다음 커서. 결과 본문 없이 생성 시각·ID 내림차순으로 조회한다. 기존 원천/프로젝트 접근 검사에 실패한 실행은 제외하고 건수를 알린다. 현재 조건의 원래 분석과 이 일정의 모든 예약/재시도 실행이 대상이다.
- `GET /api/analytics/schedules/{id}/runs/{run_id}/comparison?offset=0&differences_only=true`: 이 일정의 지정 실행과 저장된 비교 대상을 읽는다. PARA별 근거는 한 번에 100건. 두 완료 결과의 비기간 조건, 상대적 기간 길이/간격, 원천, 방법 버전이 같을 때만 비교 상태를 계산한다. 실패/취소/미완료·조건 차이·이전 대상 불명은 사유를 반환한다. 현재 범위에서 볼 수 없는 결과의 내용은 반환하지 않는다.
- `AnalysisRun.comparison_run_id`, `AnalysisSchedule.outcome_run_id`, `AnalysisNotification.comparison_run_id`를 선택 필드로 추가한다. 기존 기록을 추정하여 채우지 않는다. `schedule_id, created_at, id` 복합 인덱스를 추가한다. 일정 등록/조건 교체는 기준 결과를 갱신하고 예약·재시도·완료 조정은 실제 비교 연결을 유지한다. 과거 알림의 연결은 변경하지 않는다.
- 화면 응답은 작업공간·일정·선택 실행을 검증하며, 사용자 변경 시 별도 캐시 키를 사용한다. 읽기 동작은 원천 조회/작업 제어/알림 확인 처리를 수행하지 않는다.

## 관리 데이터 백업·임시 복원 검증

계약 기준은 `backend/app/recovery_contract.py`, 소비 타입은 `frontend/src/recovery.generated.ts`이며 기존 생성 계약 검사에 포함한다. `/api/admin/recovery`는 관리자 역할을 실제 저장 상태로 재검사한다.

- `GET /api/admin/recovery`: 지원 여부·현재 작업 여부·전체 보관 수·생성 가능 여부·최근 20개 기록·보관 안내를 반환한다. 기록에는 공개 상태/단계/시각/크기/테이블·행 수/검사 결과/재검증 가능 여부/작업공간 내 폴더만 포함한다. DB URL·키·테이블 내용은 반환하지 않는다.
- `POST /api/admin/recovery`: `{workspace_token, request_id}`. 요청 ID는 32자리 소문자 hex. 전체 관리 DB 스냅샷을 백업하고 임시 복원을 검증한다. `202 BackupView` 응답 후 background task 실행.
- `POST /api/admin/recovery/{id}/verify`: 같은 요청 형식으로 저장된 파일을 재검증한다. 백업 시점 이후 변경은 포함하지 않는다.
- 관리 DB advisory lock으로 생성/검증의 동시 실행을 막는다. 파일 기록의 요청 ledger는 생성 및 반복 검증 후에도 멱등성을 유지하며 다른 동작에 같은 요청 ID를 재사용하면 거절한다. 요청 작업공간이 바뀌면 409, 진행 중/보관 한도 409, 대상 없음 404, 지원하지 않는 구성 422, 상태/저장 실패 503.
- 상태는 `running|verified|attention|failed|interrupted`. 프로세스가 중단되어 lock 없이 남은 running은 interrupted로 표시한다. 최대 50개, 자동 삭제 없음. SHA-256, 실제 임시 복원, 전체 행 해시, 흐름 연결, 현재 암호화 키 해독, 복원본 자동 작업 중단, 임시 DB 정리를 검증한다.
- 운영 관리 DB 덮어쓰기나 원천 데이터 쓰기 경로는 없다. 로컬 런타임·대상·실행 파일 경로를 제한하고 외부 업로드는 받지 않는다. 자세한 운영 범위는 `METADATA_RECOVERY.md` 참조.

## 관리자 운영 점검

`GET /api/admin/operations` → `OperationsStatus {workspace_token, checked_at, checks, notes}`. 계약 기준은 `backend/app/operations_contract.py`, 생성 소비 타입은 `frontend/src/operations.generated.ts`이며 기존 생성 계약 검사에 포함한다.

- 각 점검은 `{id,title,scope,status:ok|attention|unknown|info,message,guidance,observed_at?,action?}`다. action은 `database|activity|knowledge|schedules|recovery|llm_settings` 중 하나이며 기존 화면 이동만 수행한다.
- 저장된 사용자 활성·관리자 권한을 다시 검사한 뒤 조회한다. 요청 작업공간은 공통 middleware에서 고정한다. 관리 DB 조회 실패는 503이며 원천 연결 실패는 해당 점검의 확인 필요로 반환해 백업 안내를 유지한다. 민감한 연결·예외 원문을 응답하지 않는다.
- 분석·질문·일정은 현재 원천 DB 전체를 집계하고 분석 결과 본문을 로드하지 않는다. 다른 DB의 예약은 건수만 구분한다. 실패·기준 확인 집계에는 과거 기록도 포함한다.
- 원천 읽기 전용 연결 확인, 현재 사용자 키 해독과 저장된 연결 기록, 백업 기록만 확인한다. 모델 호출·데이터 변경·작업 실행·백업 생성은 하지 않는다.
- 처리기 관측은 응답 서버의 프로세스 메모리에만 저장한다. 반환값·예외·기존 작업 상태 전이를 유지하며 중지·재시작 전 완료는 새 세대 관측을 덮어쓰지 못한다. DB 마이그레이션은 없다.
- 화면은 명시적인 점검 버튼으로만 요청하고 사용자·작업공간별로 캐시를 분리한다. 60초 지난 결과를 안내하며 실패·범위 불일치 시 이전 결과를 현재 결과로 표시하지 않는다. 자세한 판단 기준은 `OPERATIONS_CHECKS.md` 참조.

# 원천 공정·측정 항목 보충 (2026-10-25)

- Inline의 측정 항목은 `operation+parameter` 쌍이다. 원본 실행에 보존된 SQL의 공정/PARA 제한을 따라 항목 표시를 만든다. `item_labels?: Record<string,string>`는 분석 결과의 표시용 부가 정보이며 원래 컬럼 키·수치·승인 내용을 변경하지 않는다.
- 검토 방향은 wafer_his의 operation별 recipe/eqp_id → Inline operation+parameter → EPM parameter다. 실제 연결·시점과 관측 관계는 데이터로 검증하며 이 방향을 인과 증명으로 사용하지 않는다.
- 알려진 측정 항목의 공정명 생략, 과거 사례를 통한 MAIN 일반화, 근거 없는 배수 표현은 챗 설명 검증에서 거절한다. 확인되지 않은 과거 측정 공정은 미확인으로 구분한다.
- 완료된 과거 실행/승인 근거 조회는 원천 기존 컬럼이 모두 동일하게 보존된 추가 컬럼만 허용한다. 데이터셋 정의/버전·기존 컬럼·공개 범위·연결·프로젝트 변경의 재확인은 유지한다. 대기/실행 중 작업에는 이 예외를 적용하지 않는다.
- 로컬 합성 DB 원천 wafer_his의 eqp_id는 검증용이다. 앱의 원천 읽기 전용 연결과 권한은 유지한다. 기존 승인 ML에 장비 변수가 자동 추가되지는 않는다.
