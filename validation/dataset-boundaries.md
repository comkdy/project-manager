# 프로젝트 데이터 경계와 원본·추가 데이터셋 구분

검증일: 2026-10-25. 실행 앱: http://127.0.0.1:8000/.

## 원인과 변경

프로젝트 목록과 AI 데이터셋 후보가 프로젝트 전용 정의와 공통 정의를 함께 반환했다. 또한 직접 작성한 SQL은 현재 프로젝트 범위를 적용하지 않아 WHERE 누락이나 잘못된 조건으로 다른 프로젝트 행을 조회할 수 있었다.

- 목록, AI 재사용, 평가 사례의 데이터셋 추천은 같은 프로젝트만 대상으로 한다. 공통 정의는 전체 프로젝트 화면에서 유지한다.
- SQL·간편 작성·카드·Python 입력은 원천 테이블에서 프로젝트 조건을 적용한 뒤 결합·집계한다. 프로젝트 구분이 없는 원천만 사용하는 요청은 차단한다. 공통 차원 정보는 프로젝트 원천과 연결할 수 있다.
- 저장된 SQL·데이터셋 버전을 수정하지 않는다. 기존 카드가 공통 정의를 명시적으로 참조하는 경우 해당 편집 연결은 유지하며 프로젝트 실행 범위를 적용한다.
- DB 원본과 추가 데이터셋을 그룹·배지로 구분한다. 이름만으로 원본을 추정하지 않고 자동 생성 식별자와 원래 테이블 조회 정의를 함께 확인한다. AI/사용자가 새로 만든 정의는 추가 데이터셋이다.
- 실행 캐시에 프로젝트의 현재 Lot 범위를 포함한다.

## 실제 DB 확인

| 범위 | DB 원본 | 추가 데이터셋 |
|---|---:|---:|
| XXXA | 9 | 6 |
| XXXB | 9 | 4 |
| XXXC | 9 | 4 |
| 공통 | 9 | 4 |

XXXA에서 공통 정의 4개가 더 이상 섞이지 않는다. 공통 정의 자체는 보존된다.

필터 없는 SQL, 다른 프로젝트 조건과 OR TRUE, CTE/UNION, Inline/EPM JOIN, 프로젝트 컬럼을 출력하지 않는 COUNT를 실행했다. 모두 XXXA 범위이며 COUNT는 명시적으로 XXXA만 조회한 대조 쿼리와 같은 169,569행이다. 기존 XXXA 데이터셋 전체를 미리 조회하고 실제 카드 7개(Inline, EPM 분포, 공정 완료 수, 소요 시간, 피벗, 간트, 다이 상관)를 재조회하여 성공했다.

상세 수치: `dataset-boundaries-live.json`.

## 회귀 검증

- 핵심 프로젝트·원본·재사용 검증: 36개 통과.
- 연결 기능 315개 실행: 초기 309개 통과, 6개는 기존의 공통 재사용/프로젝트 우회 SQL 기대값과 충돌했다. 해당 기대를 새 계약으로 갱신하고 간편 작성기의 바인딩 매개변수 호환을 유지했다.
- 관련 SQL·작성기·카드·채팅·기간 처리 파일 재검증: 65개 통과. 프로젝트·추천·간트 추가 확인: 49개 통과.
- 신규 기존 공통 카드 편집 시나리오는 테스트 스크립트의 허용 메서드 오류를 수정한 뒤 별도 실행하여 통과했다. 현재 미해결 테스트 실패 없음. 위 실행들은 중복을 포함하므로 합산하지 않는다.
- 프런트엔드 전체 테스트 228개 통과. TypeScript와 Vite 빌드 성공. 기존 Plotly 포함 번들 크기 경고는 유지된다.
- 실제 화면: XXXA의 두 그룹과 프로젝트 배지, SQL 관리의 기존 쿼리, EPM 카드 편집 및 미리보기 정상. UI 검증은 조회·열기·닫기만 수행했다.

## 기존 데이터 보존

수정 전 지문과 비교하여 32개 메타데이터 테이블의 기존 1,464행이 모두 동일함을 확인했다. 기존 프로젝트·카드·쿼리 버전·대화·지식·승인 기록을 삭제하거나 덮어쓰지 않았다.

검증으로 추가된 기록은 감사 30행, 조회 문맥 41행, 기존 데모 프로젝트 1·2의 원본 조회 정의 각 8개다. 마지막 항목은 기존 공통 원본의 프로젝트별 기본 조회 정의이며 실제 XXXA/B/C 데이터셋이나 DB 원천 테이블의 복제가 아니다.

보존 근거: `dataset-boundaries-preservation.json`. 기존행 비교는 원천 전체의 내용 해시 검증을 의미하지 않는다. 원천 DB는 읽기 전용 연결로 조회했다.
