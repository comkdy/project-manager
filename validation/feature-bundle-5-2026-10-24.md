# 정기 분석·변화 알림 구현 및 검증

작업 기간: 2026-10-23 ~ 2026-10-24 (Asia/Seoul). 앞서 추천한 여섯 우선순위를 마친 뒤 후속으로 제안했던 정기 분석·변화 알림을 구현했다. 현재 로컬 앱 `http://127.0.0.1:8000`에 반영했다.

## 구현 결과

- 완료하고 기간·조건을 확정한 업무 분석에서 정기 분석을 등록한다. 첫 실행의 기간, 재측정, 판정 기준, 승인 근거를 미리 확인한다.
- 1·6·24·168시간 간격으로 기간을 이동하며 기존 분석 대기열·사용자 제한·권한 검증을 공유한다. DB에 일정을 보관하고, 중복 일정 등록·동시 예약 실행·진행 중 겹침·밀린 일정 연속 실행을 막는다.
- 작업 상태에서 일정·알림·일시정지·재개·연결 결과를 확인한다. 상단에 미확인 알림 수를 표시하고 프로젝트 필터를 일정·알림에도 적용한다.
- 실패·취소·새 기준 확인 필요 시 일시정지한다. 기존 재시도는 원래 실행 기간·일정·부모/자식 기록을 유지한다. 재시도 성공만으로 정지된 일정을 자동 재개하지 않는다.
- 분석 → 질문 → 답변 → 승인 → 명시적인 조건 입력 → 완료된 분석 → 기존 일정 조건 교체·예약 재개가 이어진다. 승인 설명에서 수치를 자동 추정하지 않는다.
- 프로젝트 범위, 원천, 승인 지식 버전, 권한, 분석 방법이 바뀌면 조건 확인을 요구한다. 예약 작업은 조회 전과 결과 저장 전에도 범위·근거를 확인한다.
- 완료된 결과의 상태·변화 방향·표본 부족·계열 추가/누락을 비교한다. 같은 판정이 반복되면 중복 알림을 억제한다. 일정 확인은 이미 처리한 큰 결과 본문을 재조회하지 않는다.
- 실제 화면 검증 중 발견한 일정 설정/기존 작업 버튼의 중복 React key를 수정했다. 저장 후 창 닫힘, 버튼 중복 방지, 화면 갱신을 다시 확인했다.

사용법·기간 이동·알림 기준·한도는 `SCHEDULED_ANALYSIS.md`, API 계약은 `backend/app/analytics/schedule_contract.py`와 `CONTRACT.md`에 기록했다.

마지막 101개 검사는 전체 검사와 중복되는 영향 영역 재검증이다. 새로운 검사는 실제 API·worker·취소·재시도·승인·마이그레이션 경로를 사용한다. 독립된 두 PostgreSQL 연결로 같은 일정의 동시 실행이 작업 하나만 생성하는 것을 확인했다. 기존 테이블의 추가 필드가 없는 상태에서 마이그레이션을 두 번 실행해 과거 결과·질문·수집 설정 보존도 확인했다.

추가 검사 대상: 시간대가 있는 기간의 길이·간격 보존, 미확정 조건 거절, 오래된 버전·DB 토큰 거절, 권한·소유자·프로젝트 범위, 제한에 따른 대기, 일정 등록 중복, 상태별 자동 일시정지, 취소 후 연결된 재시도, 판정 변경/복귀·중복 억제, 알림 확인, 새 PARA 질문의 실제 승인과 일정 재개, 승인 근거가 조회 전/도중 바뀌는 경우 결과 미저장, 처리된 결과 본문을 읽지 않는 반복 조회.

기존 경고는 FastAPI 테스트 클라이언트의 httpx 사용 중단 예정 안내와 큰 Plotly 번들 경고이다. 검사 실패는 없다. 최초 최종 대상 실행은 존재하지 않는 테스트 파일명 때문에 수집되지 않았고, 실제 파일명으로 바로 수정하여 위 101개를 실행했다.

## 실제 화면·저장 결과 검증

임의 이름의 임시 PostgreSQL 메타데이터 DB와 읽기 전용 `wafer_fab_demo` 원천으로 `:8001` 검증 앱을 실행했다. 외부 AI 실시간 호출 대신 기존 고정 로컬 응답 어댑터를 사용했다.

브라우저에서 다음을 확인했다.

1. 완료 분석 → 정기 분석 설정 → 간격 변경 → 첫 기간 재계산 → 저장.
2. 작업 상태의 일정 표시 → 예약 일시정지 → 원래 분석으로 이동 → 기존 일정 선택 → 조건 적용·예약 재개. 저장 창이 닫히고 성공 안내가 표시된다.
3. 검증 전용으로 예약 시각을 앞당긴 뒤 실제 scheduler/worker 자동 실행. 실행 중 취소 요청과 완료, 자동 일정 일시정지 및 미확인 알림 표시.
4. 기존 재시도로 새 실행을 열고 완료. 알림 확인 완료 후 상단 미확인 개수 갱신.
5. 프로젝트 선택으로 일정·알림·작업 목록이 함께 좁혀지는 동작. 최종 브라우저 오류 로그 없음.

별도 실제 HTTP 검증은 동일 임시 앱에서 기존 질문 초안을 승인하고, 승인 참조를 연결하여 37,251행을 재분석한 뒤 기존 일정의 조건을 교체했다. 실제 프로젝트 lot 범위를 유지한 짧은 기간 분석을 정기 실행하여, 이동한 기간에 측정 데이터가 없을 때 결과 변화 알림이 생성되는 것도 확인했다.

`feature-bundle-5-qa.json`에 다음 결과를 보관했다: 취소 결과 미저장, 재시도 기간/일정 유지, 취소 알림 확인, 승인 보존, 기존 일정에 승인 조건 적용, 프로젝트 범위/필터 유지, 빈 조회 범위 변화 알림. 임시 공통 카드 2개도 유지됐다.

화면 근거:

- `feature-bundle-5-preview.png`: 첫 실행 조건 미리보기
- `feature-bundle-5-notification.png`: 취소 후 정기 일정 일시정지·알림
- `feature-bundle-5-schedules.png`: 최종 프로젝트·공통 일정과 변화 알림

검증 종료 후 임시 앱을 중단하고 생성한 임시 메타데이터 DB를 제거했다. 현재 앱에는 테스트 일정이나 알림을 등록하지 않았다.

## 현재 앱 반영·보존

기존 앱을 관리 스크립트로 중단하고, 별도 출력 폴더에서 완성한 빌드를 반영한 뒤 재시작했다. 시작 스크립트는 이전과 같은 시간 초과 표시를 냈으나, 실제 서버 시작 완료 로그·health·API·브라우저를 확인했고 재실행 시 이미 정상 실행 중임을 확인했다. 프로세스 44440에서 현재 버전이 실행된다.

`feature-bundle-5-live-before.json` / `feature-bundle-5-live-after.json` 비교:

- 프로젝트 3개, 공통 데이터셋 13개, 공통 카드 6개 유지.
- 모든 프로젝트 데이터셋·보드 정의까지 포함한 내용 해시가 동일: `108bdd300ecee628ec3e3f4bf218c8b06a9fa9f60868e56bf274aa2c6b6edba5`.
- 메타데이터/원천 건강 상태 모두 정상. 기존 작업 20개 조회.
- 현재 앱의 정기 일정·알림 0개: 사용자가 완료된 분석에서 설정해 사용하는 상태.
- 실제 현재 앱에서 새 정기 분석 영역 표시와 기존 작업 목록 연결 확인, 브라우저 오류 없음.

수정 전 소스는 `.local/feature-bundle-5-baseline-2026-10-23.zip`에 보관했다. 비밀 설정·런타임 자격증명은 포함하지 않았다.

## 적용 범위

정기 실행에는 앱 서버 실행과 해당 DB 선택이 필요하다. 알림은 앱 안에서 제공한다. 메일·메신저 전송, OS 예약 서비스, 원천 전체 실시간 감시를 추가하지 않았다. 기본 통계는 변화 판정을 하지 않으며, 다른 분석의 변화 알림도 명시한 기술 통계 기준에 따른 상태 변화 안내이다. 실제 외부 AI 품질 및 사내 SSO 검증은 이번 범위에 포함하지 않았다.
