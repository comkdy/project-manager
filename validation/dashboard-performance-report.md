# 대시보드 동시 조회 병목 개선 — 2026-10-21

## 결과

같은 3,190,500건·최근 4주·카드 7개 조건에서 변경 전 경로와 최종 구현을 비교했다. 30명 동시 조회의 보드 P95는 캐시 초기화 시 **8.285초 → 1.711초(79% 감소)**, 캐시 재사용 시 **3.833초 → 1.544초(60% 감소)**였다. 개선 후 측정 요청 1,575건은 모두 성공했다.

## 기간을 줄여도 빨라지지 않은 이유

1. **반환 결과 크기가 거의 유지된다.** 최근 4주로 원천 측정 범위는 319만 → 63.8만 건으로 줄지만 분포 카드는 여전히 표시 한도 20,000행에 도달한다. 보드 응답은 약 577KB → 498KB로만 줄었다. 기존 경로는 캐시 적중 때마다 행 전체를 잠금 안에서 깊게 복사하고, 다시 FastAPI의 재귀 변환과 JSON 인코딩을 수행했다. 큰 카드의 재귀 변환 P95만 약 41~45ms였다. 여러 응답의 변환이 공통 HTTP 이벤트 루프에 쌓였다.
2. **첫 조회가 중복 실행됐다.** 캐시가 없으면 같은 카드의 동시 요청들이 각자 DB 조회를 시작했다. 최종 비교의 30명·3회·630요청에서 변경 전 성공 623건 중 캐시 적중은 379건, 미적중은 244건이었다. 개선 후에는 609건이 결과를 재사용하고 미적중은 카드 7개 × 3회 = 21건으로 줄었다. Wafer map의 사전 확인 SQL은 카드 계산 내부에서 별도로 실행된다.
3. **캐시 적중에도 메타데이터 조회와 SQL 해석을 반복했다.** 차트 요청마다 활성 DB·사용자·최신 데이터셋·원천 목록·관계·원천 상세를 따로 읽었다. 변경 전 캐시 재사용 시험에서는 요청당 카드 검증 평균 67.8ms가 발생했다. 지금은 최신 권한·정의·스키마를 확인하되 동일한 입력의 SQL을 다시 해석하지 않는다. 메타데이터 SQL도 요청당 6회 → 4회로 줄었다.
4. **뷰 내부 전체 집계는 남는다.** EXPLAIN ANALYZE에서 `wafer_summary`의 수율은 최근 4주만 요청해도 뷰 안의 `die_results` 1,063,500행을 집계했다(병렬 스캔 평균 354,500행 × 3회). 변경 전 실행 시간은 전체 137ms, 최근 4주 133ms로 비슷했다. 날짜 조건은 Wafer 300개에 적용되지만 뷰 내부 집계까지 자동으로 줄어드는 구조는 아니다.
5. **기간 적용이 불필요한 행 번호 계산을 만들었다.** 간편 정의를 SQL 문자열로 바꾼 뒤 `ROW_NUMBER()`를 생성하여 분포 카드 계획에 WindowAgg가 추가됐다. 최종 구현은 원천 조회에 기간 조건을 직접 넣고 기존 기본키를 유지한다. WindowAgg는 없어졌지만 DB가 선택한 기본키 정렬은 남는다. 최근 4주 분포 쿼리는 이번 단일 계획 측정에서 186ms → 175ms였으며, 전체 기간 70~75ms보다 여전히 느리다. 이 인덱스 경로는 기간 밖의 84,000행도 검사한다. **기간 단축만으로 모든 쿼리가 빨라졌다고 해석하면 안 된다.**

## 변경 내용

- 차트 결과를 JSON 바이트로 한 번 변환하고 HTTP 응답에서 재사용한다. 내부 AI·이미지 출력 호출에는 독립된 객체를 제공한다.
- 같은 조건으로 동시에 조회하면 진행 중인 계산을 공유한다. 오류는 기다리는 요청에도 전달하고 다음 요청은 재시도할 수 있다.
- 기본 TTL 60초, 128항목, 16MiB 상한을 유지한다. 두 응답 바이트의 실제 크기를 모두 계산한다. 캐시 초기화 후 이전 요청이 완료되어도 새 캐시에 다시 저장하지 못한다.
- 인증·최신 버전·프로젝트 소유권·원천 표시 여부는 매 요청마다 확인한다. DB/설정 버전, 데이터셋 정의, 원천/관계 스키마, 카드 및 필터가 캐시 키에 포함된다. 카탈로그가 바뀌면 동일 버전이라도 재검증한다.
- 같은 요청에서 이미 읽은 원천 목록을 재사용하고, 관계를 쓰지 않는 정의는 관계 목록을 조회하지 않는다.
- 간편 정의의 기간 조건을 원천에 바인딩하여 집계 전에 적용한다. 프로젝트 격리와 LEFT JOIN의 행 보존을 유지한다. SQL 편집기의 원문 실행은 변경하지 않았다.
- DB 연결 풀·worker 수·표시 한도를 늘리지 않았고 원천 DB의 테이블·뷰·인덱스는 수정하지 않았다.

## 시험 방법 보완

기존의 단일 HTTP 연결 풀 시험을 먼저 그대로 재현했다. 이 방식은 서버 도착 전 대기가 크게 포함됐으며, 캐시 재사용 조건의 실제 서버 내부 동시 요청이 최대 4개에 그쳤다. 그 방식에서 원본 구현 P95 6.138초/5.650초가 응답·메타데이터 개선 후 2.992초/2.801초로 줄어드는 것을 확인했다.

최종 시험은 부하 발생기와 앱을 별도 프로세스로 분리하고 사용자마다 독립 연결 풀을 사용한다. 캐시 초기화 조건에서 서버 내부 동시 요청 최대 200개를 확인했다. 이전 보고서의 약 6초와 아래 표는 부하 발생 방식이 달라 직접 비교하지 않는다. 아래의 변경 전·후는 같은 방식으로 짝지어 측정했다.

`validation/legacy_chart_baseline.py`는 변경 전 검증·캐시·응답·기간 변환 경로를 임시 시험 프로세스 안에서 재현한다. 카드 계산 로직은 공유한다. 제품에서는 이 파일을 가져오지 않는다. 동일한 임시 DB에서 이전 경로와 최종 경로를 순차 측정했다.

## 최종 조건 및 수치

- Inline 2,100,000 + WAT 27,000 + EDS 1,063,500건. 별도로 Wafer 1,500개. 20주 분포, 최근 4주는 측정값 638,100건·Wafer 300개.
- 사용자마다 카드 7개를 동시에 요청하고 조건당 3회 반복한다. 로컬 PC, 앱 worker 1개, 기본 연결 풀이다. PostgreSQL/OS 캐시는 따뜻한 상태다.
- 초기화 조건은 각 동시 요청 묶음 전에 앱 결과 캐시를 비운다. 묶음 내 재사용은 허용한다. 재사용 조건은 미리 동일 보드를 조회한다.
- 실제 HTTP·앱 인증·권한·메타데이터·읽기 전용 원천 DB 경로를 사용한다. 클라이언트별 연결 풀을 별도 프로세스에서 구동한다. 동일 로컬 테스트 관리자 권한이며 사내 SSO 부하는 포함하지 않는다.
- 시간은 사용자 한 명의 카드 7개 요청이 모두 종료될 때까지다. 실패도 집계하며 실패한 보드 시간을 성공한 완전 로딩으로 간주하지 않는다. 브라우저 그림 그리기는 제외한다.

| 동시 사용자 | 범위 | 캐시 | 이전 P95 | 개선 P95 | 이전 오류 | 개선 오류 |
|---:|---|---|---:|---:|---:|---:|
| 5 | 전체 20주 | 초기화 | 1.520초 | 0.429초 | 0/105 | 0/105 |
| 5 | 최근 4주 | 초기화 | 1.697초 | 0.545초 | 0/105 | 0/105 |
| 5 | 최근 4주 | 재사용 | 0.609초 | 0.228초 | 0/105 | 0/105 |
| 30 | 최근 4주 | 초기화 | 8.285초 | 1.711초 | 7/630 | 0/630 |
| 30 | 최근 4주 | 재사용 | 3.833초 | 1.544초 | 6/630 | 0/630 |

변경 전 오류 13건은 HTTP 전송 `ReadError`다. API 또는 DB SQL 오류로 단정하지 않는다. 중간 비교에서도 같은 종류의 전송 실패가 관찰됐고 개선 후에는 전송/HTTP 오류 모두 0건이다.

30명 초기화 조건의 서버 내부 처리 P95는 4.783초 → 0.734초, 캐시 재사용은 2.322초 → 0.114초였다. 클라이언트 도착 전 대기는 별도 기록했다. 단계별 타이밍에는 서로 포함되는 값이 있어 합산하지 않는다.

## 검증 및 한계

- 관련 backend **209 passed**: 동시 실행 공유, 오류 후 재시도, 캐시 초기화 충돌, TTL/용량, 응답 독립성, 스키마 변경, 초안 격리, 최신 버전, 숨긴 원천, 프로젝트 격리, 읽기 전용 SQL, ISO/KST 기간, 집계 및 LEFT JOIN, 카드 표현식·패널·AI·이미지 출력.
- 이번 성능 작업에서 제품 UI와 프런트엔드 파일은 변경하지 않았다.
- 재시작 후 health 200, 실제 카드 7개 모두 200, 후속 조회 7개 모두 캐시 재사용. 재시작 전후 내용 지문 동일: 데이터셋 10개·카드 7개·대시보드 v34 보존.
- 임시 DB는 종료 시 식별자를 확인한 후 삭제했다. 사용자 DB와 프리셋은 수정하지 않았다.
- 같은 조회 조건을 공유하는 순간 동시 부하다. 30명이 서로 다른 SQL/필터를 쓰면 공유 효과가 줄어든다. 사내 DB의 뷰·인덱스·네트워크와 장시간 부하는 별도 검증 대상이다. 원천 뷰의 전체 내부 집계는 남아 있다.
- 이 부하 측정 당시에는 차트 정기 자동 조회가 없었다. 후속 변경으로 대시보드를 보는 동안 60초마다 차트를 조회하고 서버의 60초 이하 캐시 및 진행 중 요청을 공유한다. 탭을 숨기거나 대시보드를 나가면 주기 조회를 중단한다. 30초 간격 DB 연결 상태 확인은 별개다. 후속 검증은 `VALIDATION.md`의 대시보드 자동 갱신 항목을 참고한다.
