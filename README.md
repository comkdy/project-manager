## Windows에서 실행

Python 3.11 이상, Node.js와 pnpm이 필요합니다. 개발은 Python 3.13에서 검증합니다. Codex에 번들된 Node·pnpm도 자동으로 찾습니다. PostgreSQL은 프로젝트 안의 `.local`에 독립적으로 준비하므로 Docker나 관리자 설치가 필요하지 않습니다.

프로젝트 루트의 PowerShell에서:

```powershell
uv venv .venv --python 3.13
uv pip install --python .venv\Scripts\python.exe -e .\backend
.\scripts\setup-database.ps1
.\scripts\seed-demo.ps1 -Profile dev
.\scripts\start-app.ps1
```

`uv`가 없다면 `python -m venv .venv`와 `.\.venv\Scripts\python.exe -m pip install -e .\backend`를 사용할 수 있습니다.

앱 주소: **http://127.0.0.1:8000**. `start-app.ps1`이 프런트엔드 의존성을 설치·빌드하고 숨겨진 프로세스로 서버를 실행합니다. 이후 빌드가 그대로라면 `-NoBuild`로 실행할 수 있습니다.

로컬 데모는 `AUTH_MODE=local_admin`, `DEMO_MODE=true`로 실행하며 **테스트 관리자**로 자동 로그인합니다. 아이디·비밀번호 입력이 필요하지 않습니다. 이 모드는 loopback 접속에서만 허용하며 사내 운영에는 `AUTH_MODE=sso`를 사용합니다. 기존 버전의 비밀번호 로그인과 세션은 더 이상 인증에 사용하지 않습니다. `.env`, `.local`과 로그는 Git에서 제외됩니다.

```powershell
.\scripts\stop-app.ps1
.\scripts\stop-database.ps1
```

앱 로그는 `.local/app.stdout.log`, `.local/app.stderr.log`에 있습니다. 스크립트는 이 프로젝트에서 만든 프로세스·DB만 관리합니다.

## 사용할 수 있는 기능

- 전체 프로젝트 / 프로젝트 탭, 날짜·Lot·Wafer 필터, 팀 공용 대시보드.
- KPI, scatter, bar, line, histogram, box, wafer map, 간트 카드. 이동·크기 조절·복제·삭제·저장과 동시 편집 충돌 확인.
- 카드별 데이터셋·버전·X/Y·그룹·집계·필터·팔레트·축 범위 설정과 미리보기.
- 간편 편집기에서 Plotly Python 스크립트로 전환해 복합 차트와 다양한 trace를 작성합니다. 카드별 격리 실행, 지원 문법과 AI의 데이터셋 재사용 정책은 [PLOTLY_SCRIPT_CARDS.md](PLOTLY_SCRIPT_CARDS.md)를 참고하세요.
- Plotly 상호작용과 PNG/SVG 이미지 내보내기. 이전 Seaborn 카드도 현재 화면에서는 Plotly로 표시합니다.
- 컬럼명 클릭으로 불러온 100행 안에서 오름차순 → 내림차순 → 정렬 해제(불러온 순서)를 반복합니다. 정렬할 때 서버를 다시 조회하거나 페이지를 이동하지 않습니다. 커서 페이지 방식 데이터 탐색과 폼·SQL 편집기로 파생 컬럼을 만듭니다. 원본 열을 대체하는 식도 파생 데이터셋 안에서만 적용됩니다.
- 공통 테이블에서 프로젝트별 조회 쿼리를 저장합니다. 프로젝트 탭에서 공통 데이터셋을 다듬으면 해당 프로젝트 전용 정의를 새로 만들며 다른 프로젝트의 정의는 바뀌지 않습니다.
- 데이터셋 목록·쿼리 관리·일반/Python/간트 카드의 데이터셋 선택에서 **공통 / 프로젝트 전용**을 표시합니다. 이 표시는 정의의 소유 범위이며, 실제 조회 행은 SQL과 프로젝트 조건에 따릅니다.
- 쿼리 관리에서 과거 버전 조회와 파생 데이터셋 새 버전 저장. 대시보드 카드는 조회할 때 해당 데이터셋의 최신 버전을 사용하며, 카드 제목 위에 실제 계산에 사용한 버전을 표시합니다. 데이터셋 변경으로 필요한 컬럼이 없어지면 카드 설정을 수정해야 합니다.
- 기존 쿼리를 업데이트하기 전에 **변경 영향 확인**에서 컬럼 추가·삭제·타입 변경과 영향을 받는 프로젝트·카드를 확인합니다. 카드 설정의 호환성을 검사하며 Python 실행 결과나 업무 의미를 보장하지 않습니다. 호환 문제가 있으면 확인 표시 후 저장할 수 있고, 버전 충돌 시 최신 목록을 확인해 다시 검토합니다. 새 데이터셋 저장은 기존 흐름을 유지합니다.
- 목록·표·쿼리 관리는 같은 데이터셋 이름을 사용하며 원본 테이블명도 함께 표시합니다. 쿼리 관리를 열어도 이름에 접미사를 붙이지 않으며, 현재 범위의 데이터셋은 기본적으로 새 버전으로 저장합니다.
- 오른쪽 채팅 패널은 쿼리 작성·데이터셋 생성·카드 구성을 별도 Skill로 처리합니다. 카드에 필요한 데이터셋이 없으면 SQL 작성부터 이어서 처리하고, 사용자가 검토한 뒤 데이터셋과 카드를 함께 저장합니다. 검증·조회·저장 Tool과 사내 모델 연결 구조는 [AI_CHAT_WORKFLOW.md](AI_CHAT_WORKFLOW.md)에 정리했습니다.
- SQL·카드 채팅은 현재 DB에서 사용할 수 있는 승인 지식을 참고하고, 제공한 정의·매핑 버전을 표시합니다. 같은 용어에 여러 정의가 있으면 먼저 선택하며 미리보기·저장 때도 승인 상태를 다시 검사합니다.
- AI 채팅의 분석 요청은 **조건 확인·수정**으로 이어집니다. 사용자가 기존 분석 화면에서 기간·시간대·대상·반복 측정·판정 기준을 확인한 뒤 실행하며, 미정 조건은 기존 질문함으로 연결됩니다. 일반 수동 분석은 기존 실행 흐름을 유지합니다.
- SQL·카드·지식 편집 내용은 이 브라우저에 자동 보관됩니다. 닫거나 새로고침한 뒤 **비교·복구**로 되살리고, 서버 내용이 바뀌었으면 최신 내용과 비교한 뒤 저장 검사를 다시 거칩니다. 사용자·권한·작업공간·프로젝트별로 분리하며 조회 결과와 접속 정보는 보관하지 않습니다.
- **재시도·취소**: 작업 상태와 분석 상세에서 대기·진행 작업을 취소하고 실패·취소 완료 분석을 같은 조건으로 다시 실행합니다. 원래 기록과 질문·답변·승인을 보존하며 취소 요청과 완료를 구분합니다. 미확정 AI 조건안 취소와 관리자 지식 수집 제어도 연결됩니다.
- **분석 기록**에서 분석·실행 전 조건안·관리자 지식 수집을 함께 확인하고 기존 결과·질문·조건 검토로 이동합니다. 원천 조회 시각, 읽은 범위의 마지막 측정 시각, 카드 조회 시각을 구분합니다. 상세 범위와 제한은 [EDIT_RECOVERY_AND_ACTIVITY.md](EDIT_RECOVERY_AND_ACTIVITY.md)를 참고하세요.
- 관리자: 사번별 역할·활성 상태, 원본 테이블·컬럼 등록, 다대일 관계 등록, 변경 이력.
- 기존 **프로젝트 > 대시보드 / 데이터 관리**와 데이터 생성·쿼리·카드 편집은 화면과 권한을 그대로 유지합니다. 이번에 추가한 **원인 및 영향 분석 · 분석 기록**만 질문과 결과 중심으로 정리합니다. **AI 지식**은 상단 메뉴와 기존 지식 목록·검색·질문·검토 화면 및 권한을 그대로 유지하며, 백업·복구 및 운영 점검 화면/API는 제거했습니다.

480px 이하의 좁은 화면에서는 카드를 1열로 표시합니다. 팀 공용 배치를 유지하기 위해 드래그 배치 편집은 더 넓은 화면에서 제공합니다.

조회자는 데이터와 카드를 조회할 수 있습니다. 편집자는 카드·파생 정의·채팅 제안을 관리합니다. 관리자는 사번별 앱 권한·원본 설정까지 관리합니다. 로그인과 이름·팀 정보는 사내 SSO·디렉터리가 관리하며 앱에서는 비밀번호를 발급하거나 수정하지 않습니다. 모든 사용자는 모든 프로젝트를 조회할 수 있으며 프로젝트별 보안 격리는 이 버전의 기능이 아닙니다.

## 더미 데이터와 의미

`projects → lots → wafers` 관계와 공정·검사 장비, `inline_measurements`, `wat_measurements`, `die_results`를 생성합니다. `wafer_summary`는 wafer 단위로 먼저 집계한 읽기 전용 뷰입니다.

- 개발 프로필: 3개 프로젝트, 6개 Lot, 150개 wafer, 약 12만 측정·die 행.
- 성능 프로필: 60개 Lot, 1,500개 wafer, inline 200만 행 이상과 die 100만 행 이상.
- ID와 seed에 따른 값은 프로필·생성 배치 크기에 영향을 받지 않으며 개발 데이터는 성능 데이터의 부분집합입니다.
- 장비 편차·시간 변화·wafer 가장자리 패턴·특정 Lot 이상을 넣고 정상 대조군을 유지합니다.
- EDS는 wafer당 검사 회차 하나이며, 수율은 `검사 완료 PASS die / 검사 완료 die`입니다. 여러 wafer의 수율은 die 수로 가중 집계하며 미검사 die는 분모에서 제외합니다.
- Inline–WAT 비교는 `DEP/thickness`와 `run 1/VTH`의 wafer별 평균을 연결합니다. 서로 다른 항목·단위를 섞거나 측정행을 직접 다대다 연결하지 않습니다.
- Wafer map에는 하나의 wafer를 선택해야 합니다.

```powershell
.\scripts\seed-demo.ps1 -Profile perf -Replace
.\.venv\Scripts\python.exe demo\verify.py --profile perf
```

프로필 변경은 개발용 데이터 교체 작업입니다. 생성기는 loopback의 지정된 demo DB와 식별 marker를 확인하며 업무 원본 URL을 사용하지 않습니다. 생성 후 검증 결과와 이상 manifest는 `.local`에 저장됩니다. 새 프로필을 넣은 뒤에는 대시보드 새로고침으로 캐시를 우회하세요.

## 실제 PostgreSQL 연결

등록된 DB를 선택한 뒤 휴지통 모양의 **등록 삭제** 버튼으로 앱의 접속 정보를 지울 수 있습니다. 활성 DB는 다른 DB를 활성화한 뒤 삭제합니다. 실제 DB·테이블·데이터와 앱의 대시보드·데이터셋·쿼리 및 테이블 표시 설정은 보존됩니다. 같은 DB를 다시 등록하면 기존 구성을 사용할 수 있습니다. 초기 환경 설정에서 가져온 DB도 등록 삭제 후 자동으로 다시 나타나지 않습니다.

오른쪽 위 **워크스페이스 관리 → DB 설정 → DB 추가**에서 `Host`, `Port`, `DB name`, `User`, `Password`를 입력합니다. **연결 확인**은 접속과 읽기 전용 권한, 테이블 탐색을 검사하며 설정을 저장하지 않습니다. **DB 등록**은 검사를 통과한 접속 정보를 저장하며 현재 활성 DB를 바꾸지 않습니다. 등록된 DB를 선택하고 **이 DB 활성화**를 누르면 앱 전체에서 사용할 DB가 전환됩니다. 활성 DB는 항상 하나이며, 전환 실패 시 기존 DB를 유지합니다. 상태는 초록(연결됨), 노랑(확인 중), 빨강(실패), 회색(미확인)과 텍스트로 표시하고 활성 DB에는 **활성** 배지를 붙입니다. 목록에서 DB를 선택하면 테이블을 확인하고 **접속 정보** 팝업에서 설정을 수정할 수 있습니다. 현재 활성 DB의 접속 정보를 저장하면 검증 후 같은 DB에 다시 적용합니다.

`APP_DATABASE_URL`은 사용자·대시보드·데이터셋·DB 접속 등록 정보·개인 LLM 키를 저장하는 **앱 관리 DB** 연결이며 `.env`에 필요합니다. 분석할 **원천 DB**는 웹의 DB 설정에서 등록·활성화하므로 `.env`에 `SOURCE_DATABASE_URL`을 넣지 않습니다. 저장된 연결은 서버 재시작 후에도 복원됩니다. 실제 사내 운영에서는 `DEMO_MODE=false`, `AUTH_MODE=sso`로 설정합니다. DB 연결 설정은 관리자만 사용할 수 있습니다.

사내로 옮길 때에는 앱 관리용 PostgreSQL DB를 준비하고 `APP_DATABASE_URL`의 주소·계정·비밀번호를 해당 환경에 맞게 변경합니다. 로컬 데모의 `127.0.0.1:55432/wafer_app` 주소는 사내 DB 주소가 아닙니다. 새 관리 DB를 사용하면 빈 앱 설정으로 시작합니다. 기존 설정을 이전하려면 관리 DB 백업과 DB 접속 정보·LLM 키의 암호화 키도 함께 이전해야 합니다. 사내 분석 DB에 앱 설정 테이블을 자동 생성하는 방식은 아닙니다.

비밀번호를 포함한 접속 URL은 Fernet으로 암호화해 앱 메타데이터 DB에 저장하고 API 응답과 변경 이력에는 반환하지 않습니다. 암호화 키는 `DB_CREDENTIALS_KEY`로 지정하거나, 처음 저장할 때 생성되는 `.local/db-credentials.key`를 사용합니다. 이 파일의 접근을 서비스 계정으로 제한하고 **메타데이터 DB와 키를 함께 보존하되 별도로 백업**해야 합니다. 다른 PC로 옮길 때도 같은 키가 필요합니다. 키가 없으면 다른 DB로 임의 전환하지 않고 연결 오류를 표시합니다.

원천 계정에는 `CONNECT`, 스키마 `USAGE`, 필요한 테이블의 `SELECT`만 부여합니다. 관리자 권한, DB·스키마 생성 및 임시 테이블 권한, 테이블 쓰기 권한, 시퀀스 변경 권한이 있으면 앱이 연결 사용을 거부합니다. `PUBLIC`이나 상속한 역할의 권한도 확인해야 합니다. 원천 연결의 기본 트랜잭션과 매 조회 트랜잭션은 읽기 전용으로 설정됩니다. 저장된 쿼리·이력은 별도의 앱 메타데이터 DB에 기록합니다.

DB 설정에서 연결하면 새 DB의 테이블과 컬럼을 자동으로 읽습니다. 앱을 열거나 데이터셋 추가를 누를 때 목록을 새로 확인하며, 원천 테이블 선택에는 별칭 없이 DB의 `스키마.테이블명`을 표시합니다. 조회 계정에 스키마 USAGE와 테이블 SELECT 권한이 있는 일반 테이블·뷰·물리화 뷰를 대상으로 하며 시스템 스키마는 제외합니다. 기존 실제 테이블이나 인덱스를 수정하지 않습니다.

처음 발견한 테이블은 관리자 등록 없이 자동 연결하고 실제 테이블명을 이름으로 하는 기본 데이터셋 v1을 만듭니다. 컬럼명·타입·단일 기본 키를 DB 카탈로그에서 읽으며, 기본 키가 없는 테이블과 복합 기본 키 테이블도 SQL로 조회할 수 있습니다. 컬럼이 바뀌면 자동 생성 데이터셋에 새 버전을 만들고 이전 이력을 보존합니다. 사용자가 직접 편집한 쿼리는 자동으로 덮어쓰지 않습니다. 결과 컬럼 한도에 따라 초기 쿼리는 앞쪽 100개 컬럼을 선택하며 원천 컬럼 목록은 모두 불러옵니다.

소스와 데이터셋은 DB 호스트·포트·DB명으로 구분합니다. 다른 DB를 연결하면 이전 DB의 데이터셋·카드·관계는 숨겨지고, 원래 DB로 돌아오면 다시 사용할 수 있습니다. 비밀번호나 조회 계정 변경은 같은 DB로 취급합니다. 테이블이 삭제되거나 조회 권한이 사라진 경우도 다음 목록 확인 시 숨깁니다. 기존 설치의 정의는 이 기능을 처음 실행할 때 연결된 DB에 귀속됩니다.

**DB 설정에서 DB 선택 → 테이블 → 앱에 표시** 스위치로 테이블별 표시 여부를 관리합니다. 테이블명을 펼치면 실제 컬럼명과 타입도 확인할 수 있습니다. 제외한 테이블도 이 관리 목록에 남으므로 언제든 다시 켤 수 있습니다. 표시 설정은 DB별로 저장되고 현재 DB에는 재시작 없이 적용됩니다. `.env`의 `TABLE_IGNORE`는 사용하지 않습니다. 구버전 환경 설정의 연결·표시 설정을 읽는 호환 경로는 남아 있지만, 신규 설정은 웹에서 관리합니다.

제외된 테이블은 탐색·등록 후보, 데이터셋·관계·AI 목록에서 숨기며 새 등록과 직접 SQL 조회도 거부합니다. 해당 테이블을 직접 참조하는 기존 데이터셋과 대시보드 카드도 숨깁니다. 원천 데이터와 저장된 정의·이력은 삭제하지 않으므로 스위치를 다시 켜면 복원됩니다. 이 설정은 명시한 테이블에 적용되며, DB 뷰 내부의 의존 테이블까지 추적하지 않습니다.

자동 연결에서는 프로젝트 소속이나 테이블 관계를 컬럼명만 보고 추측하지 않습니다. 특정 프로젝트 조건은 쿼리에서 지정하며, 관리자가 이미 설정한 컬럼 범위·프로젝트 매핑은 유지합니다. 관리자 수동 등록과 기존 폼 관계 설정에서는 고유·비NULL 키를 사용합니다. SQL 편집기에서는 자동 연결된 원천 테이블도 JOIN할 수 있습니다. 데모 전용 이름과 차트 템플릿은 데모 초기화에만 사용합니다.

## 사내 SSO와 사용자 관리

`expert-agent`의 로그인 구조를 참고했습니다. 브라우저가 보낸 SSO 쿠키를 **백엔드에서 검증한 뒤 사번을 확인**하고, 사내 디렉터리에서 이름·팀을 가져옵니다. 검증되지 않은 쿠키 내용이나 요청 헤더의 사번·역할은 신뢰하지 않습니다.

```dotenv
AUTH_MODE=sso
SSO_COOKIE_NAME=회사에서_지정한_쿠키명
SSO_BOOTSTRAP_ADMIN_EMPLOYEE_ID=초기_관리자의_사번
DEMO_MODE=false
```

초기 관리자 사번 설정은 앱 권한을 미리 등록하는 용도이며 SSO 검증을 우회하지 않습니다. 이후 관리자가 사번별 `admin/editor/viewer`와 활성 상태를 관리합니다. 처음 검증된 사용자는 조회자로 자동 등록됩니다. 이름·팀은 사내 디렉터리 값으로 동기화하며 앱의 역할·활성 상태를 덮어쓰지 않습니다. 자신의 관리자 권한 제거·비활성화와 마지막 SSO 관리자 제거는 제한합니다. 동시 권한 수정은 버전 검사로 충돌을 알립니다.

**실제 사내 연결은 아직 설정되지 않았습니다.** 참고 앱에도 SSO 검증·프로필 조회의 URL과 요청/응답 계약이 없어, `backend/app/sso_adapter.py`의 `verify_sso_cookie`와 `fetch_employee_profile`을 연결 지점으로 분리했습니다. 회사 계약에 맞게 이 두 함수를 구현해야 하며 단순히 쿠키명을 설정하는 것만으로 인증이 동작하지 않습니다. 현재 미연결 상태에서는 접근을 차단하고 연결 준비 안내를 표시합니다. SSO 실패 시 테스트 관리자로 전환하지 않습니다.

SSO 모드에서는 사내 로그인 후 **로그인 상태 다시 확인**을 누릅니다. 이 앱의 버튼은 회사 전체 SSO 로그아웃을 수행하지 않습니다. 프로필 메뉴에서는 사번·이름·팀과 앱 권한을 확인할 수 있습니다. 기존 로컬 계정은 데이터 보존을 위해 남아 있으나 인증에는 사용하지 않습니다.

로컬 테스트를 다시 시작하려면 격리된 데모 DB에서 `AUTH_MODE=local_admin`, `DEMO_MODE=true`를 설정합니다. 기존 카드·데이터셋은 인증 모드를 바꿔도 유지됩니다.

```powershell
.\scripts\stop-app.ps1
.\scripts\start-app.ps1 -NoBuild
```

## LLM 연결

관리자가 `.env`에 다음을 설정하고 앱을 재시작합니다.

```dotenv
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=your-installed-local-model
```

`/chat/completions`를 지원하는 OpenAI 호환 서버를 사용합니다. `LLM_BASE_URL`에는 `/v1` 같은 API 기본 주소 또는 `/chat/completions`까지 포함한 전체 주소를 넣을 수 있습니다. 사내·로컬·공인 주소를 구분하는 모드 설정은 없으며 관리자가 지정한 주소와 모델로 연결합니다. 환경을 옮길 때 두 값을 바꾸고 앱을 재시작한 뒤 해당 서버용 개인 API 키를 프로필에 등록하면 됩니다. 모델 설치나 서버 구축은 앱이 자동 수행하지 않습니다. 링크 로컬·미지정·멀티캐스트 주소와 자동 리다이렉트는 허용하지 않으며, 다른 서버로 자동 전환하지 않습니다.

각 사용자는 오른쪽 위 **프로필 → LLM API 키 설정**에서 본인의 키를 등록·수정·삭제하고, 저장한 키로 **연결 확인**을 실행합니다. 연결 확인은 공통 모델에 짧은 요청을 보내며 업무 데이터는 보내지 않습니다. 조회자도 본인 키를 관리할 수 있지만 채팅 변경 제안은 기존처럼 편집자·관리자만 사용할 수 있습니다. 키가 없으면 채팅을 실행하지 않으며, 기존 공통 `LLM_API_KEY` 환경 변수는 더 이상 사용하지 않습니다.

API 키는 사용자 계정별로 앱 관리 DB에 암호화 저장하며 키 원문은 API 응답·감사 기록에 포함하지 않습니다. 활성 DB 전환과 무관하게 유지됩니다. 보호에 필요한 암호화 키는 앱이 `.local/llm-credentials.key`에 자동 생성하므로 `.env`에 개인 API 키나 `LLM_CREDENTIALS_KEY`를 넣지 않습니다. 이 파일은 접근 권한을 제한하고 관리 DB와 별도로 백업하세요. 암호화 키를 잃으면 사용자가 API 키를 다시 등록해야 합니다. 여러 앱 서버를 운영할 때만 비밀정보 관리 시스템에서 동일한 Fernet 암호화 키를 `LLM_CREDENTIALS_KEY` 환경 변수로 공급할 수 있습니다. 이 운영용 재정의 값은 개인 LLM API 키와 다릅니다.

앱은 등록된 컬럼·데이터셋 정의와 대화 문맥을 전달합니다. 원본 행 전체를 모델에 전달하지 않습니다. 모델 응답은 구조화된 카드/데이터셋 제안으로 검증하며, 모델에 DB 실행 권한을 주지 않습니다. 연결하지 않아도 수동 기능은 모두 사용할 수 있습니다.

## 조회·편집의 동작 범위

- 원본 조회는 전용 계정과 읽기 전용 트랜잭션을 사용합니다. SQL AST에서 단일 조회 문장만 허용하고, DDL/DML·CTE 내부 변경·잠금·외부/사용자 정의 함수·설정 변경 함수는 차단합니다. 필터 값은 파라미터 바인딩 또는 SQL AST의 문자열 리터럴로 처리하고, 컬럼명은 검증 후 인용합니다.
- SQL 편집기의 조회 SQL은 검증 후 원문 그대로 실행·저장합니다. JOIN, HAVING, CTE, 인라인 뷰, 윈도 함수, DISTINCT, ORDER BY/LIMIT, 집합 연산을 사용할 수 있습니다. 등록된 원천 테이블과 조회용 함수만 허용합니다. 원문을 임의의 정렬·WHERE·LIMIT으로 재작성하지 않고, 결과 수신량만 제한합니다.
- 간편 작성기와 초기 쿼리는 `s.lot_code`처럼 일반 이름을 큰따옴표 없이 생성합니다. 대소문자 구분·공백·예약어 때문에 필요한 식별자 따옴표는 유지합니다. 직접 작성한 SQL은 따옴표·주석·줄바꿈을 바꾸지 않으며, 간편 작성기에서 내용을 수정하지 않고 돌아와도 원문을 보존합니다. [실제 실행 경로와 검증](SQL_EXECUTION.md)을 참고하세요.
- 간편 작성기는 단일 테이블의 SELECT·FROM·WHERE·GROUP BY를 지원합니다. 두 편집기를 왕복할 수 있으며, 간편 작성기로 표현할 수 없는 SQL은 간편 탭만 비활성화합니다. 간편 작성기의 filter는 집계 전 WHERE 조건입니다.
- 프로젝트에서 기존 폼 정의를 열 때 프로젝트 WHERE 조건을 SQL에 표시합니다. 이후 SQL 조회 범위는 작성된 WHERE 조건을 따릅니다. 프로젝트별 데이터셋 소유권과 버전 접근 제한은 유지됩니다. 저장된 SQL의 결과에 대시보드 필터·집계를 적용할 때는 원문을 내부 쿼리로 사용합니다.
- 데이터 관리 표는 100행씩 불러오며 헤더 정렬은 불러온 행 안에서만 수행합니다. API의 최대 조회 한도는 1,000행입니다. SQL 결과의 페이지 조회는 결과 순서를 따라 이동하므로 일관된 순서가 필요하면 SQL에 ORDER BY를 지정합니다.
- 간편 편집기의 산점도·box 표본은 최대 20,000행입니다. 현재 표본은 고유 키 순서의 앞쪽 행이며 무작위 표본이 아닙니다. 카드에 `앞쪽 행 표본`과 잘린 결과를 표시합니다. 전체 분포 판단에는 서버 집계 histogram을 함께 사용하세요. Python 카드의 입력 한도는 [PLOTLY_SCRIPT_CARDS.md](PLOTLY_SCRIPT_CARDS.md)를 참고하세요.
- 조회 기본 제한은 30초, 결과 캐시는 60초입니다. 새로고침은 캐시를 우회합니다. 프로젝트·필터·데이터셋 버전이 서로 다른 결과는 캐시를 공유하지 않습니다.
- Python 카드 실행은 별도 프로세스와 동시 실행 제한을 사용합니다. 화면의 Plotly 차트를 이미지로 내보내면 상호작용이 없는 정적 이미지가 됩니다.
- 로컬 단일 서버를 기준으로 합니다. 사내 서비스로 확장할 때 HTTPS, SSO 쿠키의 도메인·전달 정책, 정확한 허용 origin, 운영 백업·모니터링을 구성해야 합니다. 원본 DB 직접 수정은 별도 확장 범위입니다.

### 프로젝트별 SQL 관리

물리 테이블은 공통으로 유지하며 앱 DB에는 프로젝트별 SQL 정의와 버전만 저장합니다. 예를 들어 프로젝트 1에서 다음처럼 계산 컬럼을 만들 수 있습니다.

```sql
SELECT *,
       value * 1000 AS value_scaled,
       CASE WHEN value < lsl OR value > usl THEN 'FAIL' ELSE 'PASS' END AS quality
FROM public.inline_measurements
WHERE project_id = 1
```

현재 더미 측정 테이블의 프로젝트 키는 `project_id`입니다. 화면에는 프로젝트 이름을 표시하며, 이름 변경에 영향을 받지 않는 ID로 조회합니다. 실제 소스의 프로젝트 구분 컬럼은 관리자가 등록합니다.

`데이터 관리 → 데이터셋 추가`에서 원천 테이블을 선택해 프로젝트 전용 정의를 만듭니다. 기존 정의는 `쿼리 관리`에서 편집합니다. 데이터셋 이름 아래에는 사용 중인 원천 테이블명(스키마 포함)을 표시하며 JOIN한 테이블도 함께 표시합니다.

`간편 작성기 ↔ SQL 편집`은 단일 테이블의 SELECT·FROM·WHERE·GROUP BY 범위에서 양방향으로 전환됩니다. JOIN·HAVING·인라인 뷰 등은 SQL 편집기에서 실행할 수 있고 간편 작성기는 비활성화됩니다. 탭 전환만으로 SQL을 다시 생성하지 않으며, 간편 작성기의 내용을 변경할 때만 새 SQL을 만듭니다. 미리보기 성공 후 저장할 수 있습니다. `SELECT *`에 같은 이름의 컬럼을 다시 추가하면 중복 이름으로 거절됩니다. 기존 컬럼의 식·이름을 바꾸려면 원하는 출력 목록을 명시하세요.

간편 작성기의 column은 이름 버튼으로 나열합니다. 버튼을 누르면 SQL 표현식·출력 이름 순서로 편집하거나 출력에서 제외할 수 있습니다. 표현식은 필수이며 원본 컬럼도 실제 참조 이름을 표시합니다. 출력 이름은 선택 사항으로, 비우면 표현식을 따릅니다. `컬럼 추가`에서 계산·집계 구분 없이 원하는 식을 입력합니다.

SQL 표시에서는 원본과 출력 이름이 같은 단순 컬럼의 `AS`를 생략합니다. 다른 출력 이름, 계산식, JOIN 컬럼의 구분용 이름에는 필요한 별칭을 유지합니다.

예를 들어 inline 측정에 장비 이름을 붙이고 Lot·장비별로 집계할 수 있습니다.

```sql
SELECT m.lot_code, e.name AS equipment_name,
       COUNT(*) AS measurements, AVG(m.value) AS mean_value
FROM public.inline_measurements m
LEFT JOIN public.equipment e ON m.equipment_id = e.id
WHERE m.metric_name = 'thickness'
GROUP BY m.lot_code, e.name
HAVING COUNT(*) >= 2
```

간편 작성기의 filter는 집계 전 WHERE 조건입니다. SQL 편집기의 WHERE·HAVING 조건은 입력한 그대로 실행합니다. 데이터 관리 표는 SQL 결과를 100행씩 가져오고 헤더 정렬은 불러온 행 안에서만 처리합니다. 페이지 간 순서가 필요하면 SQL에 ORDER BY를 지정합니다.

프로젝트 전용 정의는 해당 프로젝트 탭에 나타납니다. 기존 폼 정의를 프로젝트에서 열면 생성되는 SQL에 프로젝트 WHERE 조건을 표시합니다. 직접 작성한 SQL에는 숨겨진 프로젝트 조건을 추가하지 않으므로 조회 범위는 SQL 자체를 따릅니다. 프로젝트별 쿼리 정의·버전의 접근 범위는 별도로 확인합니다.

공통 탭의 정의는 공유 기준입니다. 프로젝트 탭에서는 공유 기준을 프로젝트 전용으로 새로 저장하고, 이후 그 정의에 버전을 추가할 수 있습니다. 원본 행·스키마와 과거 데이터셋 버전은 유지됩니다. **기존 카드는 참조 중인 데이터셋의 최신 버전으로 조회**하며, 자동 갱신과 수동 새로고침 뒤에는 실제 계산 버전을 표시합니다.

## 검증과 개발

AI 챗은 승인된 평가 사례와 계산 결과를 근거로 중요한 관측, 다음 확인 사항, 해석 한계를 자연어로 설명합니다. 문단별 근거를 펼치면 인용 원문과 원본 분석을 확인할 수 있습니다. 설명 자체는 새 승인 지식이나 새 계산이 아니며, 기존 데이터셋·카드 제안과 검토·승인 흐름을 그대로 사용합니다. 이전 대화도 승인 상태와 데이터 범위를 다시 확인한 뒤 설명을 복원합니다.

연결 기능의 검증 범위와 실행 명령은 [회귀 검증 기록](REGRESSION.md)을 참고하세요.

2026-10-24 화면 개편: EPM 중심 / Inline 중심의 두 질문에서 Recipe 비교를 시작합니다. 결과는 평균·변동 폭·표본 수와 기존 판정을 요약하고, 기준을 넘은 항목을 먼저 표시합니다. 개별 Inline–EPM 측정값을 짝지은 상관·인과 분석은 아직 제공하지 않습니다. 기존 분석·질문·승인·일정·알림과 저장 데이터는 유지합니다.

완료한 분석의 **정기 분석 설정**에서 확정한 조건을 반복 실행할 수 있습니다. **분석 기록**에서 예약 일시정지·재개, 실패·취소 작업의 재시도, 변화·기준 확인 알림을 함께 확인합니다. 질문·승인 후 완료한 새 분석 조건을 기존 일정에 적용할 수 있습니다. 기간 이동과 알림 기준은 [정기 분석 안내](SCHEDULED_ANALYSIS.md)를 참고하세요.

일정의 **실행 이력·결과 비교**에서 예약 실행과 재시도 기록을 열 수 있습니다. 변화 알림의 **변화 근거 비교**는 당시 비교한 두 결과의 PARA별 수치·판정 기준·계열 추가/누락을 보여 줍니다. 승인 후 일정 조건을 바꿔도 과거 비교 대상은 유지하며, 조건이 다른 분석이나 비교 대상이 없는 과거 기록은 제한 이유를 표시합니다.

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests demo\test_generator.py -q
```

통합 테스트는 `DEMO_MODE=true`인 분리된 PostgreSQL에서만 실행합니다. 역할, 프로젝트 범위, 페이지 이동, 원본 SQL과 수율 일치, 카드 저장 충돌, 계산식 검증·버전 유지, PNG/SVG, LLM 미설정과 모의 내부 API 계약을 검증합니다. 실제 LLM 품질 검증은 사내 서버 설정 이후 필요합니다.
